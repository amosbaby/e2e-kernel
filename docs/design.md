# e2e-kernel（e2e 验证内核）设计

> 状态：v1 设计。标【未证实】的要先实测。Playwright 的说法来自官方文档（playwright.dev，2026-11-26 取）。

## 1. 要做什么，为什么

做一个专门用来做 e2e 验证的本机应用：让 AI agent 快速在浏览器里把一件事验一遍，给出带证据的结论。

现有做法大致两类，各解决了一半：

- **带护栏的只读复测**：拦下写请求，结论附证据，检查能固化成用例重跑。代价通常是绑定一种浏览器和一种 agent、只能读、上手重。
- **通用的浏览器控制 MCP**：轻、不绑 agent、过程可见，跑在用户日常浏览器上。代价是不在网络层拦写、agent 拿到用户全部登录、没有用例层。

这个应用把两边的核心思路合在一起，并且要求**浏览器和 agent 都能换**。

使用时刻：

1. 代码在 GitHub，由 agent 或人触发发布，发布后通知 agent 去测试环境（必要时生产）验证。
2. 在本地 dev server 上验证。
3. **问题复核**：不一定跟着一次开发。直接让 agent 调这个工具，去某个环境（本地、测试或生产）复核某个问题是否存在，比如有人报了 bug、想确认线上是否复现。结论是「存在 / 不存在 / 无法判断」加证据。

## 2. 目标、非目标、反目标

### 目标

| # | 目标 |
|---|---|
| G1 | **改完即验、有问题即复核**：一句话指令（可带 PR 或工单链接）→ agent 多轮操作页面 → 结论加证据。不要求先有一次开发或一个用例，拿到一个环境和一句描述就能开始 |
| G2 | **agent 可换**：能跑 shell 命令的 agent 用 CLI；MCP 客户端用薄 MCP 壳。v1 验收在 Claude Code 和 Codex CLI 上各跑通一遍 |
| G3 | **浏览器可换**：内核只通过一份驱动协议碰浏览器。v1 只实现 Playwright 驱动 |
| G4 | **写按域名规则放行**：工具不内置「哪个是测试、哪个是生产」。没配置的域名默认可读可写；用户可配「默认只读」的域名（默认拦写、按声明放行）和「默认不允许」的域名（默认拒跑、有开关） |
| G5 | **批准绕开 agent**：在只读域名上放行写、打开不允许的域名、改域名规则都要人批准，agent 拿不到也造不出批准 |
| G6 | **专用 profile，按域名组隔离**：profile 由内核管的 Chromium 持有，agent 碰不到日常浏览器；把域名编成不同的组，各组的登录互不相见（比如生产一组、测试一组） |
| G7 | **证据**：每次运行一份 `report.html` 和 `result.json`，含截图、实测值、被拦下和被放行的写 |
| G8 | **验证过程能存成用例**，一条命令重跑，重跑不调模型 |
| G9 | **省 token**：文本优先、一次调用批量执行多步、截图默认缩小；给 agent 的使用说明首读 5 千 token 以内 |
| G10 | **站点知识外置**：仓库不内置任何真实站点的规则、账号或用例（见第 3 节） |

### 非目标（v1 不做）

- CI、夜间无人值守回归（登录始终要人做）。
- 第二种浏览器驱动（比如「日常 Chrome 加扩展」）。只保证驱动协议不挡路。
- gif 录屏、视觉回归对比、性能测量。
- 自动清理写操作造成的数据。
- 内核自己调模型做语义判定。
- macOS 以外的平台（Playwright 本身支持 Linux，但 v1 只在 macOS 上验证）。
- 反向验证（把每条 assert 改坏确认能判 fail）。

### 反目标（出现就算失败）

- agent 能自己批准放行写、自己打开不允许的域名、自己改域名规则。
- 没声明的写被悄悄放行。
- 编在不同组里的域名，登录出现在同一个 profile 里。
- 仓库里内置了任何真实站点的域名规则。
- 报告、日志、命令输出里出现 token、cookie、密码。
- 有检查被跳过，结论却写「通过」。
- agent 第一次用要先读几万 token 的文档。
- 仓库里出现真实主机名、账号、租户名或任何站点私有的信息。

## 3. 约束

### 仓库不带站点知识

- **站点知识全部外置**：域名规则、读型 POST 白名单、身份探针脚本、登录识别规则、用例，都放在用户本机的配置目录或用户自己的私有位置，不进本仓库。仓库只定义格式，带一份用 `example.com` 和本地 fixture 写的示例。
- **测试只用仓库自带的本地 fixture 页面**，不依赖任何真实站点。
- 开源许可证：MIT。

### 其他

- **安全要求**：密钥不硬编码、不进日志和输出；外部输入都要校验；文件路径要规范化并限制在预期目录内。
- **登录由人做**：内核不输入密码，不处理验证码。
- **写拦截有边界**：带副作用的 GET 拦不住，所以「只读」不等于绝对安全；登录着要紧账号的域名应配成「默认不允许」。
- **Playwright 官方文档确认的事实**：
  - `browserContext.route()` 对 context 内任何页面生效，含弹窗和新开链接。
  - 被 Service Worker 接管的请求 `route()` 拦不到，官方建议 `serviceWorkers: 'block'`。
  - `browserContext.routeWebSocket()` 自 v1.48 起可用，只对调用之后新建的连接生效。
  - `addInitScript` 在页面脚本之前运行，子 frame 挂上或导航时也运行。
  - 同一个 user data 目录不能同时启动两个浏览器实例。
  - 不支持自动化 Chrome 的默认用户 profile。
- **【未证实】要在第一个里程碑实测**：
  1. `route()` 是否覆盖跨进程 iframe 里的请求。
  2. `route()` 是否拦得住原生表单提交（文档只明说了 XHR 和 fetch）。
  3. 人在 Playwright 自带的 Chromium 里手动登录目标环境能否成功（有的登录服务会拒绝被自动化控制的浏览器）。这一项由使用者在自己的环境上测，结果不进仓库。

## 4. 路线

| 路线 | 做法 | 取舍 |
|---|---|---|
| **A（选定）** | 新仓库。本机常驻内核加 Playwright 驱动 | 可写、可核验要紧的域名、agent 可换，这几个前提都能正着设计；代价是全部从零写 |
| B（没选） | 现成 Playwright MCP 加一份使用说明 | 写策略和批准只能靠 agent 自律，违背 G4、G5 |

选 A 的另一个理由：「同一个 user data 目录不能同时起两个实例」意味着每个 profile 只能由一个进程持有，常驻进程本来就躲不掉。

## 5. 设计

### 5.1 总体结构

```
agent 面    CLI（主）      薄 MCP 壳      使用说明（一份短文档）
               └──────┬──────┘
                 本机 socket（JSON 协议）
┌──────────────────────────────────────────────────┐
│ 内核（常驻进程）                                   │
│  域名规则 · 会话 · 写策略 · 批准 · 证据 · 用例      │
│  判定（纯函数）                                    │
└──────────────────────┬───────────────────────────┘
                 驱动协议（操作 + 能力声明）
浏览器面    Playwright 驱动（v1）      其他驱动（以后）
            每个 profile 一个 Chromium 实例
```

- 内核是唯一持有浏览器、profile、会话、批准记录的进程。
- CLI 和 MCP 壳都是薄客户端，只做参数校验和转发。
- **内核由人或 agent 运行 `e2k start` 启动**（或设成登录时自启），CLI 不自动拉起；TTY 检查证明不了是人，不当作安全边界。理由：agent 的沙箱里可能起不了浏览器、弹不出对话框、写不了状态目录。CLI 发现内核没在跑，就返回「要人处理」（22）并给出启动命令。

### 5.2 域名规则

**工具不内置任何「这是测试、那是生产」的判断**：公开的工具分辨不了。没配置的域名默认可读可写；用户在本机配置里给域名定规则。

| 模式 | 谁属于它 | 能不能开 | 写 |
|---|---|---|---|
| 默认 | 没配规则的所有域名，含回环地址 | 能 | 全放行，仍记录 |
| 只读 | 配在「默认只读」名单里的域名 | 能 | 默认拦，按批准过的声明放行 |
| 不允许 | 配在「默认不允许」名单里的域名 | 默认拒；每次运行经人批准后才开 | 批准时由人选「只读」或「可写加放行清单」 |

- **匹配**：精确主机名，或 `*.example.com` 这样的后缀通配。更具体的规则优先；同样具体时「不允许」压过「只读」。
- **模式按顶层页面所在的主机算**。一个「默认」模式的页面（比如本地 dev server）发出的请求全部放行，包括发往只读、不允许域名的接口的写。这些写不拦，但逐条记进报告的「这次动了什么」，发往只读、不允许域名的单独标出。
- **M2a 的落实（`sessions.ts`）**：有效只读 = 会话被 `open --readonly` 强制，或会话主页面的顶层主机只读，或请求所在页的顶层主机只读，任一成立即只读。主页面顶层导航时，导航前的主机和导航目标取并，所以只读页向默认主机的原生表单 POST 也拦得住。放行的导航不立刻改主机：导航可能根本没提交（下载、204），也可能被重定向到内核看不见的地方，所以目标先记成「待定」，和原主机一起参与有效模式；有「已提交」的证据（主页面其他请求带着的顶层地址、`open` 之后和每次 `step` 结束后读到的页面地址）才把主机定下来并清掉待定，模式变了才进时间线。被拦的导航什么都不改；非 http(s) 的页面地址不动。`open` 返回的 `mode` 是首屏之后的有效模式。弹窗和新标签页算会话的页。默认模式的页面发往只读主机的写放行，只记录（`targetMode`）。归不到任何会话的请求：只要有一个只读会话活着，或请求所在页自己的顶层主机只读，写就按只读拦（`unattributed`）。规则在 `open`、`status` 和主页面顶层导航时刷新；缓存是全局的，任何一次刷新读到新文件，所有会话的后续请求立刻按新规则判，不必等自己的下一次导航；规则文件有错，新的 `open` 被拒，已开的会话按上一份好规则继续、`step` 带提示。驱动拦不了网络请求（`networkInterception: false`）时，只读的 `open` 被拒、不开页。「不允许」模式和放行声明（批准通道）不在 M2a，规则文件现在只收 `readonly` 和 `default`。
- **M2b 的落实（`rules.ts`）**：`rules.json` 的可选键 `groups`：每组 `name`（只收小写 `^[a-z0-9_-]{1,32}$`，`default` 保留，因为 macOS 默认不分大小写）、`hosts`（必填非空）、`loginHosts`、`readPosts`、`persistedQueries`、`logout`、`identity`。**没编组的主机即 `default` 组**，它的登录主机是顶层 `loginHosts`、其余清单为空；`groupOf(host)` 在所有组的 `hosts` 里取最具体的（精确优先、通配后缀越长越具体），主机不合格也落到 `default`。同一个 `hosts` 写法不能进两个组，某组的 `loginHosts` 不能落进另一组的 `hosts`，各接口的主机必须在本组的 `hosts` 或 `loginHosts` 里。接口写法是 `{ method, origin, path[] }`：只收不带查询串、片段、凭据的 http(s) 地址，`*` 独占一段（不能在主机里），只匹配由字母、数字、`.`、`_`、`~`、`-` 组成且不以点开头的一段（白名单，`;` 路径参数和任何 `%` 编码都不收）；不用正则匹配 URL，请求带查询串、协议或端口不同一律不匹配（失败关闭）。身份探针是 CSS 选择器加期望文本，不执行配置里的脚本，快照引用、引擎前缀、`>>`、role、XPath 写法都拒。`ModeResolver.isLoginHost(host, group)` 只看那个组的登录主机。这一步只解析和校验，组还没接进会话（后续步骤接）。
- **域名规则存在用户本机的配置目录里，不在仓库里。改规则要人批准**（走 5.4 的通道），批准记录绑定配置内容。否则 agent 把一个域名从「不允许」里删掉，就绕开了全部策略。
- **域名组**（可选）：把一批域名编成一组，给这组单独的 profile、登录主机列表、登录页识别规则、读型 POST 白名单、身份探针。没编组的域名共用一个 `default` profile。想让两批登录互不相见，就把它们编成两个组。
- **第一次在某个域名上登录时问一句模式**：由内核弹确认框，让人选这个域名用「默认 / 只读 / 不允许」，不在终端里问（终端里的提问 agent 也能答）。默认全放行的前提下，这是唯一一处主动提醒。
- **运行中跳转**：顶层页面或新标签页跳到「不允许」的域名，会话停下并报原因；跳到「只读」的域名，写策略随之切到只读；跳到属于另一个组的域名，会话停下并提示另开会话（那边的登录不在这个 profile 里）。跳到本组的登录主机按「等登录」处理。
- 页面里嵌的第三方 iframe（客服、支付、验证码）不让会话停下，它们发出的请求按顶层页面的模式处理。
- **借用登录**：本地页面需要远端登录态时，`open` 时指明用哪个组的 profile。这个组里含「不允许」的域名时，每次运行要人批准一次（只问是否允许），因为动用了那边的登录。
- **身份探针**（可选）：一段读页面里当前账号或租户的脚本，加一个期望值。配了就每轮核对，对不上就停。同一 profile 里多个会话共用登录态，账号或租户可能被别的会话切走。

### 5.3 写策略

**位置**：放在网络层，用驱动提供的请求拦截（Playwright 是 `browserContext.route()`）。理由：页面里的任何脚本、agent 注入的脚本发出的写都过这一层。若实测发现跨进程 iframe 或原生表单提交拦不住，退回两层：网络层加一段在页面脚本之前注入的页面内拦截脚本（改写 `fetch`、XHR、`sendBeacon`）。

**规则**（顶层页面处于「只读」模式时；「不允许」的域名经批准以只读方式打开时也一样）：

1. `GET`、`HEAD`、`OPTIONS` 放行。
2. `POST`、`PUT`、`PATCH`、`DELETE` 默认拦：给页面回一个假的失败响应，并记进报告。
3. **读型 POST 白名单**，按域名组配置：换 token 的请求（拦了会把整个 profile 登出）、GraphQL 查询、搜索类接口。
4. GraphQL 按 operation 判：查询放行，mutation 拦；放行声明细到 operation 名。只带 hash 的持久化查询要能识别。
5. 登出导航拦下，记进报告。
6. Service Worker 一律 `block`。
7. 页面发往其他域名的请求（监控、埋点、第三方 iframe）同样按这套规则：读放行，写拦下并记进报告；确有需要的可以声明放行。
8. WebSocket：v1 不拦，报告里注明「有 WebSocket 连接，不受写策略管」（拦了页面多半坏掉，先如实标出）。

**M2a 的口径（`write-policy.ts`、`sessions.ts`）**：只读模式只放行读（`GET`、`HEAD`、`OPTIONS`，不带请求体）和严格的 GraphQL query：方法 `POST`、`Content-Type` 为 `application/json` 或 `application/graphql`、URL 上没有 `query` 参数、每个操作都是带选择集的 `query`。严格 query 放行时不跟重定向（驱动在首跳 3xx 中止，那条写记成被拦的 `redirected-write`）。还没有读型 POST 白名单和放行声明，持久化查询（只带 hash）一律拦。`GET`、`HEAD` 的 URL `query` 参数是 mutation，或判不出但含 `mutation` 一词，也拦。拿不准的、判断出错的一律拦（失败关闭）。拦下的请求不管方法都进记录，原因（`method`、`graphql-mutation`、`persisted-query`、`redirected-write`、`unattributed`）和判定当时的有效模式一起记下。给页面的回应：子资源请求回 `403` 加 JSON `{"error":"blocked by e2k read-only mode"}`（跨源时页面上表现为 CORS 错误），导航回一张写着同一句话的 `403` 页面。`step` 的结果带 `writesBlocked`（本批执行期间被拦下的本会话请求数；执行结束后才到的「重定向被拒」算进下一批，未归属的不算）和 `notices`，退出码不变。

**放行声明**：`{ 方法, URL 模式, GraphQL operation 名（可选） }` 的列表，挂在一次会话或一个用例上。声明只是「请求」，生效以内核里的批准记录为准（见 5.4）。

**留痕**：报告里单列「这次动了什么」，逐条列出放行的写（方法、URL、时间、状态码，请求体脱敏后截断）。发出请求的页面（或其顶层文档）有密码类输入框、或判断不出时，只记方法、URL、状态，请求体不记（`bodyOmitted`，失败关闭）。报告在写请求段开头还有一张汇总表，按主机 × 方法分组，列放行和拦下的个数（只有主机名，不带路径和请求体；未归属的写不计入）；GraphQL 的写再分 query、mutation、subscription、unknown（`result.json` 的 `writes.summary`、各条写的 `graphql`），这只是给人读的分组，拦不拦由严格 query 检查定（见 M2a 的口径），拿不准的（持久化查询、被截断的请求体、括号不平衡的文档）一律是 unknown，不算 query。

### 5.4 批准

需要人批准的四件事：

| 事 | 何时问 | 记不记住 |
|---|---|---|
| 改域名规则、域名组、读型 POST 白名单 | 每次改动 | 记住，绑定配置内容；内容变了重新问 |
| 在「只读」域名上放行一组写 | 第一次用这组声明时 | 记住。同一域名下，已批准过的声明及其子集不再问；多出新的一条就只问新的 |
| 打开「不允许」的域名 | 每次运行 | 不记住。每次都问，默认「只读」；选「可写」要同时确认放行清单 |
| 借用含「不允许」域名的组的 profile | 每次运行 | 不记住。只问是否允许 |

- **放行声明可以在会话中途追加**：agent 往往要等写被拦下才知道该声明什么。`step` 带上新声明 → 内核返回「等人批准」→ 批准后同一会话接着跑，页面状态保留。
- **「一次运行」**指一个会话或一次 `run`。并行开第二个会话要再问一次。
- **「不允许」域名上的放行清单由 agent 在 `open` 时声明**，人在确认框里只做选择：拒绝、只读（声明整体不放行）、可写（只放行清单里的）。会话中途追加声明就再弹一次确认框。
- `open` 阶段等批准时还没有会话：内核给这次请求一个请求 id，确认框里显示它，agent 重试时带上。

流程：

1. agent 的调用需要批准时，内核返回「等人批准」加一段给人看的摘要（域名、模式、要放行的写）。这是可恢复的阻断，不是失败。
2. 内核自己向人发起确认（v1 用 macOS 原生对话框，由内核进程弹出）。
3. 人确认或拒绝后，agent 重试原调用即可继续。

硬约束：

- **批准不能经由 CLI 或 MCP 的协议完成**。没有 `approve` 子命令，没有对应的 MCP 工具。
- **弹框的实现（M2b）**：对话框实现注入内核（`startKernel` 的 `dialog`），测试用假实现，`e2k start --no-dialogs` 换成永远弹不出的实现，只会让结果更严（22）。真实现用 `osascript`，正文、标题、按钮名一律经 argv 传入，不拼进脚本；输出只认去掉一个末尾换行后的精确形状，其余（非 0 退出、被杀、多出的输出、不在按钮里的名字）按弹不出处理；不在图形登录会话里（`launchctl managername` 不是 `Aqua`）一直弹不出。待批表同步返回，框在后台弹：同一时刻屏幕上最多一个框，其余排队；同一类被拒后 60 秒内直接拒，同一个请求被拒后内核重启前不再问；10 分钟内弹过 6 个框就不再弹（22）；弹不出框之后这个内核里的后续请求一律 22。对话框里显示原值，不脱敏不截断，任一行超过 200 字符或正文超过 1500 字符就直接拒绝这次请求。
- 批准记录存在内核的状态目录里，不存在用例文件里。用例文件 agent 可以改，所以它只能表达「请求」。
- **M2b 的落实：规则的批准快照（`approval-store.ts`、`rules.ts`、`mode.ts`）**：改规则一律要批准，含收紧、删文件；生效的是批准快照，不是磁盘上的 `rules.json`。批准记录 `$E2K_HOME/approvals.json`（0600、只由内核写）在内核启动时读一次，之后以内存里的为准；`update` 先写同目录随机名临时文件（`O_CREAT|O_EXCL|O_NOFOLLOW`）再 `rename`，成功了才换内存，序列化后超过 2 MB 或写不进去就抛错、内存不变。读时按「不信任」读（`O_NOFOLLOW|O_NONBLOCK`、普通文件、不超过 2 MB、形状严格），符号链接、FIFO、目录、超大、坏 JSON、多余键都算读不了：当没批准过，现有规则全部重新批准。**运行中磁盘上的文件被改、被删、换成符号链接都不让内存里的批准降级**，`externallyChanged()` 每次 `refresh` 比一次磁盘（只比哈希、从不把磁盘内容读回内存），结果只进 `status` 的提示。`refresh` 把 `rules.json` 的原文和快照原文比：一样 = 无待批；不一样且解析得了 = 待批（原文和哈希留在内存里）；改坏 = `error`（坏文件不进待批）；文件不存在而快照里有规则 = 待批的「删文件」。**待批期间的模式取已批准和待批文件里更严的那份**（任一只读即只读，所以收紧立刻生效、放宽等批准；待批是删文件则只看已批准的）；组、白名单、`loginHosts` 只认已批准的。待批的身份是原文的完整 sha256（64 位十六进制，`ModeResolver.pending().hash`），`approvePending(hash)` 比的是它，不是 16 位短哈希；`status`、报告和批准记录里存的、显示的仍是短哈希（64 位十六进制过脱敏会被抹掉）；同一组里同一个接口只能写一条 `persistedQueries`（否则差异按接口合并会漏掉新哈希，解析即报错）；批准写盘成功后 `state().approvals` 置为 `ok`。`approvePending(hash)` 只在内存里待批的哈希等于 `hash` 时，把内存里那份原文写进批准记录并生效，不重读磁盘，传旧哈希得到 false（调用方重新 `refresh`）。待批的说明 `summary` 把待批内容和已批准内容逐字段比较，放宽的排前面（读型 POST、持久化查询和新哈希、登录主机、登出被删、身份探针、主机换组、只读规则被删或改成默认），收紧的在后面；超过 12 行 `tooLong`（入口闸门的弹框据此只给「拒绝」）。`rule diff` 打印同一份完整差异，`rule list` 注明每条规则是否在快照里，`doctor` 的规则一项报「已批准 / 有未批准的改动 / 批准记录读不了」。**入口闸门（`sessions.ts` 的 `gateRules`）**：`openSession`、`beginLogin` 在规则文件有错的检查之后、做任何别的事之前先看 `pending()`；非 null 就用内容键 `rules:<已批准快照的完整哈希，没有为 none>:<待批的完整哈希，删文件为 deleted>`（`PendingRules.baseHash` 和 `hash`）向 `Approvals` 问一次；键里带基线，所以没用掉的旧批准在别的批准落盘、基线变了之后对不上新的请求（改回早先批准过的文本必须重新问），`approvePending` 成功后还把 `Approvals` 里其余已批准的 `rules:` 键一并作废（`forgetApproved`，被拒的保留）：标题「e2k：域名规则改了」，正文是短哈希加 `summary`（放宽的在前），按钮「拒绝」（默认）、「批准」，120 秒。`pending` → 21；`denied` → `usage`（冷却中是另一句）；`unavailable` → `needs-human`（22）；`approved` → 用**内存里待批的完整哈希**调 `approvePending`（不重读文件），成功就 `forget(key)` 继续，返回 false（同步调用之间不可能，只会是内核自己的 bug）抛 `internal`、不放行，`approvePending` 写盘失败抛的 `needs-human` 原样往上。`tooLong` 的框只有「拒绝」、`approveButtons` 为空，必然 `denied`。待批期间所有新的 `open`、`login`（含 `open --readonly`）都先过它，所以没有绕过的入口；收紧在批准前已按「更严合并」让已开会话的下一个请求生效。`step` 的 `notices` 在有待批时加「规则文件有未批准的改动（收紧的部分已生效）」，`approvalsChanged` 为真时加「批准记录被内核以外的进程改过，已忽略」。启动时批准记录读不了且 `rules.json` 存在：快照为空，文件自然进待批，`status`、`doctor` 报「批准记录读不了」。
- **威胁模型**：防的是 agent 走偏、误操作、图省事绕路，不防蓄意攻击的 agent。同一系统用户下的 agent 理论上能改状态目录或操控桌面，v1 不做签名之类的加固，在文档里如实写明。

### 5.5 登录和 profile

- 一个 `default` profile，加每个域名组一个 profile。每个 profile 一个 user data 目录，放在内核状态目录下，目录权限只给当前用户。
- 每个 profile 同一时刻一个 Chromium 实例；多个会话是这个实例里的多个标签页。
- `login <URL 或组名>`：内核打开对应的 profile，人在里面登录。配了登录页识别规则就按它判断登录完成，没配就由人在终端里按回车确认。
- **登录窗口里的写照只读规则拦，只有两类免拦**（M2a）：`login` 打开的窗口（含它弹出的窗口）里，(1) 请求目标主机在 `loginHosts` 里，或 (2) 是表单提交（顶层导航）且发起它的页在 `loginHosts` 的主机上（发起页的地址以驱动给的 `initiatorUrl` 为准，没有才用跟踪到的已提交/待定主机；`initiatorUrl` 是被导航替换的那份文档，iframe 的 `target=_top` 等少数导航里它不是真正的发送者）——这是 SAML POST 绑定、OIDC `form_post` 回调从身份提供方回到应用的路径。所以要把身份提供方的主机列进 `loginHosts`，回调由此自动放行，接收回调的应用主机不用列。其余一律不免：`loginHost` 页上的 fetch/XHR 写别的主机照只读规则判；托管在只读主机自己上的用户名密码表单，除非该主机也列进 `loginHosts`，否则会被拦（已知取舍）。登录页在哪个主机上，照会话主页面那套跟（起始主机、放行的导航目标作待定、非导航请求带的顶层地址作已提交的证据，顶层导航带的 `initiatorUrl`（被导航替换的那份文档的地址，通常就是发起页）是更直接的证据，先据此定下导航前页面的主机再判断——经重定向进入身份提供方、且它的自动提交页没发过别的请求时，只有这一条能认出发起页）；身份提供方页自己写的第三方主机（验证码、内嵌的 MFA 验证框、遥测）在登录起点只读时也要列进 `loginHosts`；把只读的应用主机本身列进 `loginHosts` 的代价是：登录窗口发给它的写全部免拦、也不记录；弹窗在拿到证据前按开启者已提交的主机算。不免拦的请求，有效模式取并：登录起点主机只读、页面的已提交或待定主机只读、请求自己的顶层主机只读，任一成立就按只读，走和会话相同的写策略（严格 query 照样放行且不跟随重定向）。登录请求不进任何会话记录；被拦的只在内核日志留一行（登录 id、方法、脱敏主机，不写路径和体），并累计进 `login.end` 的 `writesBlocked`，CLI 收尾时据此提示检查 `loginHosts`。`login.begin` 先刷新规则，文件有错时和 `open` 一样被拒。`login.begin` 本身仍是本机任何客户端都能发的（威胁模型已写明），弹框确认留给 M2b。会话处于「等登录」时，人在会话窗口里登录也按该会话的模式拦：要登录请用 `login`。
- 会话中发现掉线：返回「等登录」（可恢复的阻断，和失败用不同的退出码），人在同一个浏览器窗口里登好后，agent 重试即可在原页面续跑。
- **v1 一律有头运行**，窗口不抢焦点。理由：一个 profile 只有一个实例，实例启动后不能在有头和无头之间切换，而登录必须有头；一律有头就不用为了登录重启实例、丢掉其他会话的页面。顺带让过程可见。无头留到以后做 CI 时再加。
- 用 Playwright 自带的 Chromium，不碰用户的日常浏览器。
- **profile 状态和最近一次 login**：`status` 和 `doctor` 报 profile 的状态（`missing` / `never-launched` / `launched`，只表示浏览器有没有用过这个目录）和最近一次 `login` 的时间与主机。记录在 `profiles/<名字>.login.json`（0600、不跟符号链接，放在 profile 目录旁边而不是 user data 目录里，不会被浏览器或页面碰到），只在人按回车结束 `login` 时写；写失败只记日志。判断有没有登录态看这条记录，不看状态：会话窗口里手动登录不会记。`doctor` 只读，没 login 过不算失败，也不会让退出码变成 22。

### 5.6 会话和操作

三个动作，会话归内核所有，跨多次 CLI 调用存活：

- `open`：URL、视口、放行声明、可选的 profile 组（不给就由 URL 的域名推出）、可选的触屏模拟（`--touch`，只作用于这个会话的页面，不能模拟时 `open` 失败）→ 会话 id 加首屏读数。
- `step`：一批操作，按顺序执行 → 每个操作的结果。**动作执行失败**（找不到元素、超时）就停下，后面的不执行（批级 `--keep-going` 例外：失败后后面的照跑，失败截图照留，退出码仍按计数算）；**`assert` 不符不算执行失败**，记下结果接着跑。动作失败时结果可带 `hints`（诊断）：选择器匹配了多个就列出总数和前 5 个候选（每个候选一条，可写的 `>> nth=i` 和位置在名字前面），点击被遮挡就带上挡住它的元素；条目可能含页面文字，内核先脱敏、再截到 300（每条）、最多 6 条，记录里页面有密码类字段（或判不出）时只留一句固定说明。
- 每个操作的结果带 `seq`，是整个会话从 1 起的序号，跨批次连续，未执行的操作也占号，和记录、报告里的序号一致，文本输出里叫「序号」。
- `close`：收尾，生成报告。

`step` 里的操作（v1）：

| 类 | 操作 |
|---|---|
| 读 | 文本快照（无障碍树，带元素引用）、取页面文本、截图（默认缩小；可加标签、取整页或某个元素、存成 png、用 `mask` 遮住已知的敏感元素）、读 console、读网络请求摘要 |
| 动 | 点击、填写、按键、悬停、滚动、导航、设视口、等待条件（文字、元素、地址、时间，或页面安静下来的 `idle`） |
| 判 | `assert`：对一个确定值（文案、数量、颜色、字号、间距、URL、可见性）做代码比较，只有相符或不符 |
| 脚本 | 在页面里执行一段 JS 并返回结果。它只有页面脚本的权限，发出的写同样过写策略；拿不到驱动对象 |

- 元素定位统一用一种写法（Playwright 的选择器写法加快照里的引用），由驱动翻译成自己的方言。
- 闲置会话超时自动关闭并出报告；失败时保留最后一屏截图（带 `mask` 的截图失败除外：那张图没有遮罩，不留）。
- 多个会话可并行，但同一 profile 共用登录态。

### 5.7 判定和证据

- **确定值由代码判**：`assert` 的比较是纯函数，不调模型。
- **语义结论由调用的 agent 写**：agent 在 `close` 时提交每条结论和依据，报告里标明「agent 判定」。内核 v1 不调任何模型。
- **`assert` 的结果统一叫「相符 / 不符」**，不叫通过、不通过：复核问题时，`assert` 不符可能正是问题存在的证据，和总结论并排时不能让人误读。
- **总结论有两种口径**：验证改动用「通过 / 不通过」；复核问题用「存在 / 不存在 / 无法判断」。「无法判断」必须写原因（没复现条件、被写策略拦住走不下去、等登录等）。
- **每次运行一个目录**：`report.html`、`result.json`、截图、被拦下的写、被放行的写、用到的批准、域名和当时的模式。
- `result.json` 里有 `blocked`（等登录、等批准、身份不符、跳到了不允许或别的组的域名）和 `next`（下一步该谁做什么）。`blocked` 现在只有 `'login'` 和 `null`：值是会话最后一次登录墙检查（`open` 和每次 `step` 之后各做一次）的结果，收尾时仍停在登录页才是 `'login'`，中途撞到又离开了不算；等批准、身份不符、跳到不允许的域名要到 M3。撞到登录墙的实时提示仍在 `open` / `step` 的回应和退出码 20 里（见 5.9）。
- **只读相关的记录**（只加字段，`schema` 仍是 1）：`modes` 是模式变更时间线（`at`、已脱敏的 `host`、`mode`、`reason` 为 `rule` / `forced` / `no-rule`、`rulesHash`；和上一条模式相同就不记）；`modes[*]` 另带 `pendingRulesHash`（变化当时待批规则文件的短哈希，没有为 null）；`rules` 是收尾时的规则 `{ hash, count, pendingHash }`：`hash`、`count` 是已批准快照（没批准过是 `{ hash: null, count: 0 }`），`pendingHash` 是同时按「更严合并」生效的待批文件的短哈希（没有待批、或待批是删文件为 null）；`start.readonly` 是 `open --readonly`；`writes.blocked[*]` 带 `reason`（`method`、`graphql-mutation`、`persisted-query`、`redirected-write`、`unattributed`）和判定当时的有效 `mode`；`writes.blockedSummary` 把被拦的写按主机 × 方法 × 原因分组计数，未归属的被拦写也在里面（`unattributed: true`），不带路径和请求体；被拦的写没记原因时归入固定的 `unknown`，所以汇总的次数加起来总等于被拦的写的总数。`report.html` 为此多两段：「模式」（时间线表，只有一条且为默认模式时写「全程默认模式」，另列规则条数和哈希）和「被拦下的写（汇总）」（`blockedSummary` 的表，没有时写「没有」）；`blocked` 为 `'login'` 时「环境」一段写「收尾时停在登录页」。
- **没做的要写出来**：计划了但没执行的检查、被跳过的步骤，在结论区单列，不能并进「通过」。
- **失败分「已恢复 / 未解决」**：`close --superseded '[{"failed":n,"by":m}]'` 声明「序号 n 的失败由序号 m 取代」（序号即 `step` 输出里的 `序号`）。内核在收尾前对着记录校验：`failed` 只能是执行失败或未执行（`assert` 不符不可被取代），`by` 只能是之后完成或相符的操作，同一个 `failed` 不能出现两次；不合格是 usage 错误，会话保持打开、可重新 `close`。报告里两边的操作名和目标取自记录（已脱敏、转义），不取自 agent 的声明；报告分「已恢复的失败」（并排显示，取代者是只读操作或 `wait`、而被取代的是动作时标出；一个取代者取代多个失败时也标出）和「未解决的失败」，没被取代的未执行操作仍在「没做的」里。`tallies` 保持原始计数。
- **按条判定**：`findings` 每条可带自己的 `verdict`，报告里显示在每条前面。结论是 `pass` 时，下面任一条成立算冲突：有不符、有未解决的失败、有未解决的未执行、`--not-done` 非空、有 finding 的判定是 `fail`；`result.json` 的 `conflicts` 逐条列出原因。
- **`eval` 的记录**：源码不进记录，只记 `jsHash`（`sha256:` 加十六进制前 16 位，不加盐）；返回值整体脱敏后截到 1000 字符进记录（`output`）。页面（任一 frame）有密码类字段、或探测不出时不记返回值，改记 `outputOmitted: true`（失败关闭；`eval` 跑前跑后各探一次）；给 agent 的回应不受影响。`eval` 抛错时回应照给（脱敏过）的错误消息，记录只写固定文字并保留 `jsHash`（错误消息可能带着页面值或源码片段）；跑前跑后两次探测拿到的 frame 地址不一致（跑的时候页面换了文档）也按探不出处理。
- **截图不自动脱敏**：图里的内容没法按文字规则处理，已知敏感的元素由 agent 在 `screenshot` 里用 `mask` 遮住（每个遮罩目标至少要匹配一个元素，否则这次截图失败、不出图）；`mask` 只盖元素的包围盒。
- 所有落盘和输出先脱敏：`Authorization`、cookie、token 形态的字符串（整个值像 token 的也算，路径除外）、邮箱（含 `%40` 编码的）、表单和 URL 参数解码后再判的值、自由文本里的 `password=…`、`"token":"…"` 和 `x-api-key: …` 这类头行、配置里列出的敏感字段名。
- 报告目录在用户本机，默认不进任何仓库。旧报告按用例或会话名保留最近若干份。

### 5.8 存成用例

- 内核记录了一次会话的全部操作和 `assert`，`save-case` 把它导出成一个用例文件。在 `close` 之后按会话 id 导出。
- **从 M1 起就按可重放来记**：每个动作执行时，把快照里的临时元素引用解析成稳定的选择器一并记下，否则后面要返工。
- **导出由 agent 挑**：agent 给出要保留的步骤；不给就默认只留执行成功的动作和 `assert`，丢掉试错步骤和纯读操作。
- **语义结论不重放**：重跑时这些条目标成「未判定」，不计入通过。
- **含写的用例不保证幂等**：用例文件里标明「含写」；重跑因数据已存在而失败，如实算不通过。
- `run <用例>`：一条命令重跑，纯代码执行，不需要 agent 在场，输出同样的报告。
- 用例文件包含：起始 URL、profile 组、视口、身份期望、步骤、放行声明。它带站点信息，默认存在用户指定的位置，不进本仓库。
- 用例里的放行声明照 5.4 走批准；在「只读」域名上批准过的，重跑不再问。

### 5.9 agent 面

- **CLI**（暂名 `e2k`）：`start`、`open`、`step`、`close`、`run`、`save-case`、`login`、`status`、`doctor`、`rule`（查看和修改域名规则、域名组）。默认输出给 agent 读的紧凑文本，`--json` 出结构化结果。退出码区分：通过、不符、动作执行失败、等登录、等批准、要人处理、用法或内部错误。退出码只反映代码判的 `assert` 和执行情况（加上下一条的登录墙）；agent 写的语义结论（含「存在 / 不存在 / 无法判断」）在输出和 `result.json` 里，不映射成退出码。
- **退出码 20 已启用（内置启发式）**：`open` 和 `step` 结束时，会话主页面的顶层文档里有可见的密码类字段（`type=password`，或 `autocomplete` 含 `current-password` / `one-time-code`，不含 `new-password`；不进 iframe，穿透 open shadow DOM）就返回 20，并在 `blocked` / `next` 里提示人运行 `login`。20 优先于 10 和 11。它只是提示：会话不暂停、不关闭，也不写进 `result.json`；查不出就不报。域名组里的登录主机识别、跳转到登录主机时的暂停和 `result.json` 的 `blocked`，仍是 M2 的事。
- CLI 里改规则的子命令只是提交一份待批准的改动，批准前不生效。
- **MCP 壳**：一个 stdio MCP 服务，暴露 `open`、`step`、`close`、`run`、`save-case`、`status`、`doctor` 和只读的规则查询。`login`、改规则不经 MCP，由人在终端里做。
- **使用说明**：一份短文档，讲三个动作、退出码、遇到阻断怎么办。不为某个 agent 写专用 hook。
- **防绕过**：不做拦命令的 hook。依靠两点：profile 被内核进程占着，别的进程打不开同一个 user data 目录；批准不走 agent 的通道。

### 5.10 驱动协议

内核对浏览器只发下面这些操作：

| 组 | 操作 |
|---|---|
| 实例 | 启动（profile）、停止、健康检查 |
| 页面 | 打开（可选按页的触屏模拟：Chromium 用 CDP）、读快照、点击、填写、按键、截图（整页、元素、遮罩、格式）、设视口、等待条件（含页面空闲）、页面内执行脚本 |
| 拦截 | 注册请求拦截回调、注册页面脚本之前的注入脚本、拦导航 |
| 读数 | 当前位置（顶层 URL、弹窗、frame 列表）、拦截覆盖情况 |
| 收尾 | 关掉本会话开的标签页 |

请求回调的 `RequestInfo` 里和模式判断有关的两个地址：`topUrl` 是顶层框架导航请求的目标，其他请求是发出时那一页主框架的地址（只认 http(s)，否则 null）；`initiatorUrl` 是顶层框架导航请求发出时（路由回调运行时、导航提交之前）主框架已提交的地址，也就是「即将被这次导航替换掉的那份文档」（同样只认 http(s)）；它通常就是发起导航的页，但 iframe 的 `target=_top`、别的窗口的 `target=<窗口名>` 发起的导航，报的是被替换的那一页，不是真正的发送者，其他请求和 `topUrl` 同值。内核用 `initiatorUrl` 定主页面或登录页此刻所在的主机（会话的主页面据此先收敛 topHost 再算有效模式，登录页据此判断回调的发起页是不是 loginHost）。浏览器测试 `initiatorUrl of a form-submit navigation…` 钉住了：表单提交的 `initiatorUrl` 是提交表单那页，经 302 落地后再提交则是 302 的最终地址。

每个驱动声明自己的能力，内核和报告按能力说话：能否网络层拦截、能否覆盖跨进程 iframe、能否拦住原生表单提交、SharedWorker 发出的请求是否都经过拦截（驱动在所有页面删掉 SharedWorker：它的请求不经路由，见 `docs/m0-findings.md` §9.9；做不到就记 `not-covered`，报告提示）、是否共用用户的 profile、能否无头、选择器方言。

**能力不够就不让用在对应的模式上**：驱动做不到网络层拦截时，内核拒绝用它打开「只读」和「不允许」的域名，只能用于「默认」模式；驱动共用用户日常 profile 时，报告里如实标出。

拦截回调的决定是 `continue`（可带 `followRedirects: false`）、`fulfill`（直接回一个响应）或 `abort`。`followRedirects: false` 用于放行的写：Playwright 的路由回调只见重定向链的第一个 URL，307 / 308 的第二跳带着原方法和请求体绕过内核的判断，所以驱动用 `route.fetch({ maxRedirects: 0 })` 自己发首跳。首跳是 3xx 就中止请求，并通知 `onRequestDone({ id, status: 首跳状态, failed: true, redirectRefused: true })`（通知在中止之前发，驱动对每个请求只通知一次，先到为准）；不是 3xx 就把响应原样交给页面；发送出错一律中止，不算重定向。只对同源请求这样发；跨源请求照常放行，由浏览器自己发，浏览器才继续执行 CORS 和 SameSite（`route.fetch` 不看 SameSite 一律带 cookie，`fulfill` 还会替没有 ACAO 的响应补上 CORS 头）。请求完成通知的形状是 `{ id, status: number | null, failed: boolean, redirectRefused?: true }`。这样发出的请求由 Node 代发：不信任系统额外安装的根证书。

v1 只有 Playwright 驱动。验收标准之一：内核代码里除驱动目录外不出现 Playwright 的类型或调用；另有一个测试用的假驱动实现同一份协议。
