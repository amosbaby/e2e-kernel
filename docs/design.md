# e2e-kernel（e2e 验证内核）设计

> 状态：v1 设计。标【未证实】的要先实测。Playwright 的说法来自官方文档（playwright.dev，2026-11-26 取）。

## 1. 要做什么，为什么

做一个专门用来做 e2e 验证的本机应用：让 AI agent 快速在浏览器里把一件事验一遍，给出带证据的结论。

现有做法大致两类，各解决了一半：

- **带护栏的只读复测**：拦下写请求，结论附证据，检查能固化成用例重跑。代价通常是绑定一种浏览器和一种 agent、只能读、上手重。
- **通用的浏览器控制 MCP**：轻、不绑 agent、过程可见，跑在用户日常浏览器上。代价是不在网络层拦写、agent 拿到用户全部登录、没有用例层。

这个应用把两边的核心思路合在一起，并且要求**浏览器和 agent 都能换**。

使用时刻：

1. 代码在 GitHub，由 agent 或人触发发布，发布后通知 agent 去测试环境（必要时生产）验证。
2. 在本地 dev server 上验证。
3. **问题复核**：不一定跟着一次开发。直接让 agent 调这个工具，去某个环境（本地、测试或生产）复核某个问题是否存在，比如有人报了 bug、想确认线上是否复现。结论是「存在 / 不存在 / 无法判断」加证据。

## 2. 目标、非目标、反目标

### 目标

| # | 目标 |
|---|---|
| G1 | **改完即验、有问题即复核**：一句话指令（可带 PR 或工单链接）→ agent 多轮操作页面 → 结论加证据。不要求先有一次开发或一个用例，拿到一个环境和一句描述就能开始 |
| G2 | **agent 可换**：能跑 shell 命令的 agent 用 CLI；MCP 客户端用薄 MCP 壳。v1 验收在 Claude Code 和 Codex CLI 上各跑通一遍 |
| G3 | **浏览器可换**：内核只通过一份驱动协议碰浏览器。v1 只实现 Playwright 驱动 |
| G4 | **写按域名规则放行**：工具不内置「哪个是测试、哪个是生产」。没配置的域名默认可读可写；用户可配「默认只读」的域名（默认拦写、按声明放行）和「默认不允许」的域名（默认拒跑、有开关） |
| G5 | **批准绕开 agent**：在只读域名上放行写、打开不允许的域名、改域名规则都要人批准，agent 拿不到也造不出批准 |
| G6 | **专用 profile，按域名组隔离**：profile 由内核管的 Chromium 持有，agent 碰不到日常浏览器；把域名编成不同的组，各组的登录互不相见（比如生产一组、测试一组） |
| G7 | **证据**：每次运行一份 `report.html` 和 `result.json`，含截图、实测值、被拦下和被放行的写 |
| G8 | **验证过程能存成用例**，一条命令重跑，重跑不调模型 |
| G9 | **省 token**：文本优先、一次调用批量执行多步、截图默认缩小；给 agent 的使用说明首读 5 千 token 以内 |
| G10 | **站点知识外置**：仓库不内置任何真实站点的规则、账号或用例（见第 3 节） |

### 非目标（v1 不做）

- CI、夜间无人值守回归（登录始终要人做）。
- 第二种浏览器驱动（比如「日常 Chrome 加扩展」）。只保证驱动协议不挡路。
- gif 录屏、视觉回归对比、性能测量。
- 自动清理写操作造成的数据。
- 内核自己调模型做语义判定。
- macOS 以外的平台（Playwright 本身支持 Linux，但 v1 只在 macOS 上验证）。
- 反向验证（把每条 assert 改坏确认能判 fail）。

### 反目标（出现就算失败）

- agent 能自己批准放行写、自己打开不允许的域名、自己改域名规则。
- 没声明的写被悄悄放行。
- 编在不同组里的域名，登录出现在同一个 profile 里。
- 仓库里内置了任何真实站点的域名规则。
- 报告、日志、命令输出里出现 token、cookie、密码。
- 有检查被跳过，结论却写「通过」。
- agent 第一次用要先读几万 token 的文档。
- 仓库里出现真实主机名、账号、租户名或任何站点私有的信息。

## 3. 约束

### 仓库不带站点知识

- **站点知识全部外置**：域名规则、读型 POST 白名单、身份探针脚本、登录识别规则、用例，都放在用户本机的配置目录或用户自己的私有位置，不进本仓库。仓库只定义格式，带一份用 `example.com` 和本地 fixture 写的示例。
- **测试只用仓库自带的本地 fixture 页面**，不依赖任何真实站点。
- 开源许可证：MIT。

### 其他

- **安全要求**：密钥不硬编码、不进日志和输出；外部输入都要校验；文件路径要规范化并限制在预期目录内。
- **登录由人做**：内核不输入密码，不处理验证码。
- **写拦截有边界**：带副作用的 GET 拦不住，所以「只读」不等于绝对安全；登录着要紧账号的域名应配成「默认不允许」。
- **Playwright 官方文档确认的事实**：
  - `browserContext.route()` 对 context 内任何页面生效，含弹窗和新开链接。
  - 被 Service Worker 接管的请求 `route()` 拦不到，官方建议 `serviceWorkers: 'block'`。
  - `browserContext.routeWebSocket()` 自 v1.48 起可用，只对调用之后新建的连接生效。
  - `addInitScript` 在页面脚本之前运行，子 frame 挂上或导航时也运行。
  - 同一个 user data 目录不能同时启动两个浏览器实例。
  - 不支持自动化 Chrome 的默认用户 profile。
- **【未证实】要在第一个里程碑实测**：
  1. `route()` 是否覆盖跨进程 iframe 里的请求。
  2. `route()` 是否拦得住原生表单提交（文档只明说了 XHR 和 fetch）。
  3. 人在 Playwright 自带的 Chromium 里手动登录目标环境能否成功（有的登录服务会拒绝被自动化控制的浏览器）。这一项由使用者在自己的环境上测，结果不进仓库。

## 4. 路线

| 路线 | 做法 | 取舍 |
|---|---|---|
| **A（选定）** | 新仓库。本机常驻内核加 Playwright 驱动 | 可写、可核验要紧的域名、agent 可换，这几个前提都能正着设计；代价是全部从零写 |
| B（没选） | 现成 Playwright MCP 加一份使用说明 | 写策略和批准只能靠 agent 自律，违背 G4、G5 |

选 A 的另一个理由：「同一个 user data 目录不能同时起两个实例」意味着每个 profile 只能由一个进程持有，常驻进程本来就躲不掉。

## 5. 设计

### 5.1 总体结构

```
agent 面    CLI（主）      薄 MCP 壳      使用说明（一份短文档）
               └──────┬──────┘
                 本机 socket（JSON 协议）
┌──────────────────────────────────────────────────┐
│ 内核（常驻进程）                                   │
│  域名规则 · 会话 · 写策略 · 批准 · 证据 · 用例      │
│  判定（纯函数）                                    │
└──────────────────────┬───────────────────────────┘
                 驱动协议（操作 + 能力声明）
浏览器面    Playwright 驱动（v1）      其他驱动（以后）
            每个 profile 一个 Chromium 实例
```

- 内核是唯一持有浏览器、profile、会话、批准记录的进程。
- CLI 和 MCP 壳都是薄客户端，只做参数校验和转发。
- **内核由人或 agent 运行 `e2k start` 启动**（或设成登录时自启），CLI 不自动拉起；TTY 检查证明不了是人，不当作安全边界。理由：agent 的沙箱里可能起不了浏览器、弹不出对话框、写不了状态目录。CLI 发现内核没在跑，就返回「要人处理」（22）并给出启动命令。

### 5.2 域名规则

**工具不内置任何「这是测试、那是生产」的判断**：公开的工具分辨不了。没配置的域名默认可读可写；用户在本机配置里给域名定规则。

| 模式 | 谁属于它 | 能不能开 | 写 |
|---|---|---|---|
| 默认 | 没配规则的所有域名，含回环地址 | 能 | 全放行，仍记录 |
| 只读 | 配在「默认只读」名单里的域名 | 能 | 默认拦，按批准过的声明放行 |
| 不允许 | 配在「默认不允许」名单里的域名 | 默认拒；每次运行经人批准后才开 | 批准时由人选「只读」或「可写加放行清单」 |

- **匹配**：精确主机名，或 `*.example.com` 这样的后缀通配。更具体的规则优先；同样具体时「不允许」压过「只读」。
- **模式按顶层页面所在的主机算**。一个「默认」模式的页面（比如本地 dev server）发出的请求全部放行，包括发往只读、不允许域名的接口的写。这些写不拦，但逐条记进报告的「这次动了什么」，发往只读、不允许域名的单独标出。
- **M2a 的落实（`sessions.ts`）**：有效只读 = 会话被 `open --readonly` 强制，或会话主页面的顶层主机只读，或请求所在页的顶层主机只读，任一成立即只读。主页面顶层导航时，导航前的主机和导航目标取并，所以只读页向默认主机的原生表单 POST 也拦得住。放行的导航不立刻改主机：导航可能根本没提交（下载、204），也可能被重定向到内核看不见的地方，所以目标先记成「待定」，和原主机一起参与有效模式；有「已提交」的证据（主页面其他请求带着的顶层地址、`open` 之后和每次 `step` 结束后读到的页面地址）才把主机定下来并清掉待定，模式变了才进时间线。被拦的导航什么都不改；非 http(s) 的页面地址不动。`open` 返回的 `mode` 是首屏之后的有效模式。弹窗和新标签页算会话的页。默认模式的页面发往只读主机的写放行，只记录（`targetMode`）。归不到任何会话的请求：只要有一个只读会话活着，或请求所在页自己的顶层主机只读，就按只读拦：写（`unattributed`）、带请求体的安全方法（`unattributed`）、URL 像 mutation 的 GET/HEAD（`graphql-mutation`），与会话路径的 ②③ 同口径（终审 I-1：弹窗第一个导航曾只看方法名，失败开放）。规则在 `open`、`status` 和主页面顶层导航时刷新；缓存是全局的，任何一次刷新读到新文件，所有会话的后续请求立刻按新规则判，不必等自己的下一次导航；规则文件有错，新的 `open` 被拒，已开的会话按上一份好规则继续、`step` 带提示。驱动拦不了网络请求（`networkInterception: false`）时，只读的 `open` 被拒、不开页。「不允许」模式和放行声明（批准通道）不在 M2a，规则文件现在只收 `readonly` 和 `default`。
- **M2b 的落实（`rules.ts`）**：`rules.json` 的可选键 `groups`：每组 `name`（只收小写 `^[a-z0-9_-]{1,32}$`，`default` 保留，因为 macOS 默认不分大小写）、`hosts`（必填非空）、`loginHosts`、`readPosts`、`persistedQueries`、`logout`、`identity`。**没编组的主机即 `default` 组**，它的登录主机是顶层 `loginHosts`、其余清单为空；`groupOf(host)` 在所有组的 `hosts` 里取最具体的（精确优先、通配后缀越长越具体），主机不合格也落到 `default`。同一个 `hosts` 写法不能进两个组，某组的 `loginHosts` 不能落进另一组的 `hosts`，各接口的主机必须在本组的 `hosts` 或 `loginHosts` 里。接口写法是 `{ method, origin, path[] }`：只收不带查询串、片段、凭据的 http(s) 地址，`*` 独占一段（不能在主机里），只匹配由字母、数字、`.`、`_`、`~`、`-` 组成且不以点开头的一段（白名单，`;` 路径参数和任何 `%` 编码都不收）；不用正则匹配 URL，请求带查询串、协议或端口不同一律不匹配（失败关闭）。身份探针是 CSS 选择器加期望文本，不执行配置里的脚本，快照引用、引擎前缀、`>>`、role、XPath 写法都拒。`ModeResolver.isLoginHost(host, group)` 只看那个组的登录主机。组已接进会话和登录页：`open`、`login.begin` 按域名所在的组选 profile，会话里拦跨组导航（见下面「M2b 的落实（选 profile、借用、跨组导航）」）。
- **域名规则存在用户本机的配置目录里，不在仓库里。改规则要人批准**（走 5.4 的通道），批准记录绑定配置内容。否则 agent 把一个域名从「不允许」里删掉，就绕开了全部策略。
- **域名组**（可选）：把一批域名编成一组，给这组单独的 profile、登录主机列表、登录页识别规则、读型 POST 白名单、身份探针。没编组的域名共用一个 `default` profile。想让两批登录互不相见，就把它们编成两个组。
- **第一次在某个域名上登录时问一句模式**：由内核弹确认框，让人选这个域名用「默认 / 只读 / 不允许」，不在终端里问（终端里的提问 agent 也能答）。默认全放行的前提下，这是唯一一处主动提醒。M2b 里选项是「取消 / 默认 / 只读」（不允许是 M3）；M3 已落实为两步框（见下面「M3 的落实（不允许模式）」的 R1，用户决定），落实见 5.5。
- **运行中跳转**：顶层页面或新标签页跳到「不允许」的域名，会话停下并报原因；跳到「只读」的域名，写策略随之切到只读；跳到属于另一个组的域名，会话停下并提示另开会话（那边的登录不在这个 profile 里）。跳到本组的登录主机按「等登录」处理。
- 页面里嵌的第三方 iframe（客服、支付、验证码）不让会话停下，它们发出的请求按顶层页面的模式处理。
- **借用登录**：本地页面需要远端登录态时，`open` 时指明用哪个组的 profile。这个组里含「不允许」的域名时，每次运行要人批准一次（只问是否允许），因为动用了那边的登录。
- **M2b 的落实（选 profile、借用、跨组导航，`sessions.ts`）**：`open`、`login.begin` 的 `profile`（`组` 或 `组/槽`）在协议层只查类型和长度（≤65），写法由内核的 `parseProfileArg` 查，**在 `gateRules()` 之前**，写错的不会弹规则批准框；组存不存在、和域名合不合在闸门之后由 `pickProfile(host, arg)` 查，组信息只认已批准快照（`modes.groupOf` / `modes.group`），待批的组不算数。没给 `arg` 用域名所在的组；给了：组不存在 → usage「没有这个组」；等于域名所在的组 → 用它（带槽也行）；域名没编组（`default`）→ **借用**，不能带槽（usage「槽只能用在本组的域名上」）；否则 usage「这个域名属于组 X，不能用组 Y 的 profile」。借用不弹框（含「不允许」的组才弹，见 M3 的落实）、不核对账号。会话和登录页只存组**名**（`group`、`borrowed`），不存 `modes.group()` 返回的缓存对象，规则刷新、被批准的改动、调用方改写拿到的对象都不会改变它；`isLoginHost(host, login.group)` 按真组查。**本组登录态下、顶层不在本组的页面发往本组的写，按目标主机的模式判**（`groupTargets`）：会话（或登录窗口）的组不是 `default`、请求发往这个组的 `hosts`、而发出请求的页面当前顶层主机不在这个组里（含没编组的主机）时，有效模式再并上目标主机自己的模式。按事实判，不看 `open` 时有没有借用，所以「先开本组、再跳到没编组的主机、再写本组只读主机」也拦得住；页面停在本组的默认模式主机上时照旧（不并）。**跨组导航**：会话页（主页面和弹窗）和登录页的顶层导航，目标主机的组不是 `default` 也不是本 profile 的组，就回 403 页面（`这个域名属于组 X，当前 profile 是组 Y 的。请用 --profile X 另开会话。`，主机脱敏），判断在 `loginHosts` 豁免和写策略之前：会话里记成被拦的请求（`reason: 'other-group'`，不算「到过」的域名，不改主机和待定主机）、下一次 `step` 的 `notices` 带同一句（`writesBlocked` 仍计入，但不再配「只读模式」的提示）；登录页写一行日志并计入 `writesBlocked`，`login.end` 另返回 `crossGroupBlocked`（其中跨组导航的次数，为 0 时不带这个键），CLI 据此不把它们说成「被只读规则拦下」。首跳之外的重定向见下面的「冻结」。驱动认不出归属的导航（比如弹窗的第一个导航）不拦首跳。iframe 和子资源不管。`ModeResolver.group()`、`groupOf()` 返回的是批准快照里冻住的对象，调用方改写不了。`OpenResult` 带 `profile`（key）和 `borrowed`，`result.json` 的 `start.borrowed`，CLI 在借用时多打一行「借用组 X 的登录：发往 X 的写按那边的模式判；不核对账号」。
- **冻结：重定向进了别的组的域名（`sessions.ts`、驱动 `onNavigationHop` / `clearCookies`）**：首跳走请求回调，后面的跳不进路由回调（见 5.10），所以驱动对主 frame 导航被重定向之后的每一跳单独通知（`Instance.onNavigationHop`，带页面 id 和这一跳的地址；子 frame、子资源、认不出归属的不通知——弹窗的第一个导航 Playwright 还没有 frame，就属于这一类）。内核对会话页和登录页的每一跳按首跳同一条规则判：目标主机的组不是 `default`、也不是本 profile 的组，就**冻结**。跳已经发出，拦不住，只能事后：这个会话（登录页）此后**所有页的所有请求，含 GET，一律 403**（会话里记 `other-group`，登录页计入 `writesBlocked` 和 `crossGroupBlocked`），冻结期间同一浏览器实例里认不出归属的请求（弹窗的第一个导航）也一律 403，记进未归属的写，别的实例不受影响；`step` 不执行任何操作（先等清 cookie 落定），抛 `needs-human`（退出码 22，`页面经重定向进了组 X 的域名，会话已冻结`，下一步：关掉，用 `--profile X` 另开）；正在跑的 `step` 在当前操作之后停下（其余记未执行），跑完同样抛这个错，这一批做过的事在报告里；`open` 的首屏落在这里则不交出快照、关页撤销会话、同样抛这个错；对这一跳的主机 `clearCookies`（只清域名恰好是这个主机或 `.主机` 的 cookie，上级域的是同站点别的主机共用的，不动），只在这个会话所在的实例上清、不影响同实例的其他会话，跳转当时清一次、关会话（或登录）时页都关了再清一次（那一跳自己的 `Set-Cookie` 可能晚于第一次清理到达）。判断出错（组查不出）也冻结，错误提示改为「判断不出归属」。兜底：重定向的跳事件漏掉时，会话或登录页的页面地址（`step` 结束时读到的、顶层导航的发起页地址、请求带着的顶层地址）在别的组的域名上，同样冻结（`freezeIfOtherGroup`，在 `converge` 和 `followTopHost` 之前）；内核自己为被拦的跨组首跳回的那张 403 页会让页面停在别组的地址上，这个地址（去掉 `#`，最近 100 个）记在会话（登录页）里，不算被重定向带进去的。上级域（`Domain=example.com`）上的 cookie 是同站点别的主机共用的，`clearCookies` 不清，那一跳的响应若设在上级域就留着。
- **身份探针**（可选）：读页面里当前账号或租户的一处文字，加一个期望值。配了就每轮核对，对不上就停。同一 profile 里多个会话共用登录态，账号或租户可能被别的会话切走。
- **M2b 的落实（身份探针，`sessions.ts` 的 `probeIdentity`）**：探针是 CSS 选择器加期望文本（`rules.json` 组里的 `identity`），不执行配置里的脚本。**探一次**：`page.location()` 的主机经 `groupOf` 属于会话的组才探；否则 `skipped`（停在身份提供方或 `loginHosts` 的主机上、借用——会话组不等于页面主机所在的组——都是这条）。探的时候先 `read count` 目标 `css=选择器`：恰好 1 个再 `text`，trim 后等于 `expect` 才是 `ok`；≥2 个，或恰好 1 个而文字不符，才是确认是别的账号：`mismatch`；0 个时看主页面有没有可见的密码框，有（疑似登录页，身份元素本来就不在）是 `skipped`，没有是内部结果 `unverified`（没能确认，见下）。**密码框不关掉探针**：登录墙检查只是给人的提示、不是安全判断（驱动注释自认），后台设置页常有掩码显示密钥的密码框，租户被切走时若因此跳过，`step` 会照常执行；所以有密码框时也照样先数、数到 1 个照常比较。`css=` 前缀在驱动的 `locate` 里既不是快照引用、也不是 `role=…[name=…]`，落到 `page.locator(target)`，用 Playwright 的 css 引擎；`rules.ts` 的 `parseIdentity` 已经拒掉会被当成别的引擎的写法，所以拼出的目标不会换引擎。`count` 不等待，`text` 先数一遍所以也不等（元素刚好在两步之间消失才会落到 Playwright 的默认等待），探针整体再套一个 5 秒的时限（`identityProbeMs`）：驱动抛 `DriverError`、超时也是 `unverified`；别的异常原样往上抛；页面已关（会话在收尾）时读不到不算不符。**确认与没能确认分开（终审 I-6，推翻 Task 10「探针失手一律永久」的裁定）**：只有「确认是别的账号」才永久记 `mismatch`；`unverified`（0 个匹配且没有密码框、读取出错、超时）同样失败关闭，但只管这一次：`step` 抛 `needs-human`（22，「身份探针没能确认账号…，这次没有执行任何操作」，`next` 说下一次 `step` 会重新探），不执行任何操作（含放行声明的批准框），也不记在会话上；`open` 首屏同理，`OpenResult.identity` 仍报 `mismatch`、退出码 22（不加枚举值），但 `next` 是「会重新探」那句，会话里什么都不记。原因：单页应用在 `load` 之后才异步渲染页头，一次时序失手不该把整个会话判死。**身份每次探的时候从批准快照里会话所在的组现取**，不在 `open` 时缓存；组没有身份（或快照里没有这个组）时不探，`OpenResult.identity` 和 `result.json` 的 `identity` 都是 `null`。
- **探针的时机和闸门**：`open` 在首屏读完之后探一次，结果在 `OpenResult.identity`（`ok` / `mismatch` / `skipped` / `null`）；不符照样返回会话（人要看到提示），CLI 打醒目的一行、退出码 22。每次 `step` 在执行操作之前探一次，次序是 冻结检查 → 身份探针 → 放行声明的批准（`gateDeclarations`）→ 执行：账号不对时不该先弹「放行写请求」的框让人批。探针要 await 页面读取，所以 `step` 在探之前就把状态置成 `stepping`（并发的 `step`、`close` 因此是 `busy`，空闲计时暂停），探针、批准闸门、执行中任何一处抛错，`finally` 都把状态放回 `idle` 并重新计时。**`mismatch` 记在会话上，一旦不符永久不符，直到 `close`**：之后的 `step` 不再探、不执行任何操作，直接抛 `needs-human`（22，「身份探针不符：组 g 期望「…」，页面上不是」，`next` 让人确认后关掉这个会话重开），消息里只有组名和规则里写的期望文字。读到的页面文字只在内核里比较一次，不进错误消息、`result.json`、`report.html`、`kernel.log`、`step` 的返回值。只探会话的主页面；弹窗、登录窗口、借用的页面都不探。一次 `step` 里 `goto` 换了租户，要到下一次 `step` 才探得到（探针只在每批操作之前跑）。`open` 首屏不符时 `OpenResult.next` 放 `step` 错误里那句下一步提示（没在登录墙上时；`--json` 里看得到）；没能确认时 `next` 是「重新探」那句，CLI 的醒目行也同时说明两种情况。`result.json` 的 `identity` 是 `{ group, checks, skipped, mismatch }`：`checks` 数没被跳过的探测（做了比较的，含不符，也含读失败、超时和没读到元素这几次没能确认的），`skipped` 数前提不满足的，报告里有一节「身份探针」只写组名和次数。
- **M3 的落实（不允许模式：规则、打开、借用，`rules.ts`、`sessions.ts`）**：`rules.json` 的 `mode` 收 `deny`，同一请求的多个模式取并时 `denied` > `readonly` > `default`（`sessionMode`、规则的更严合并、差异的松紧判定都按这个序；被授权覆盖的 `denied` 先映射成 `readonly` 再取并）。规则里 deny 和更宽的通配并存时最具体的生效（精确主机优先、通配后缀越长越具体）；待批文件把主机改成 deny 立刻生效，放宽（deny 改成别的）等批准。`status`、`rule list`、`rule diff`、`doctor` 把它显示成「不允许」，`--json` 里是 `deny`，`hostModes`（登录时选的模式）也可以是 deny（两步框里选的，见 R1），同样解析成 `denied`、`reason` 是 `host-choice`，已批准的规则照旧压过它；`groupHasDeny` 不看 `hostModes`（hostModes 里的主机在做选择那一刻不在任何组的 `hosts` 里：没列明才会问；之后批准的组若含这个主机，组的借用判断 `groupHasDeny` 仍不看 hostModes，但发往它的请求按 `denied` 拦，失败关闭）。待批的规则只能收紧：基线是已批准的规则、没有命中才是 hostModes，待批文件里更严的才盖得过基线，所以待批的只读 / 默认规则降不了 hostModes 的「不允许」，要先批准；已批准的规则仍压过 hostModes（人选错了能用规则改回来）。覆盖了 hostModes 里某个「不允许」主机的新规则，差异摘要在放宽段给每个受影响主机一行 `~ 登录时选的不允许 <host> → <模式>（规则 <match>）`。驱动拦不了网络请求（`networkInterception: false`）时，deny 的 `open` 和借用含 deny 的组都在弹框之前被拒；规范化不了的主机名在 `open`、`login` 是 usage，在任何闸门之前。**打开**：主机的规则是 deny 时，`open` 每次运行都弹 `e2k：打开不允许的域名`（会话名、profile、主机，按钮「拒绝」（默认）/「只读」/「可写」），`--readonly` 不免这道闸；授权只覆盖打开的那一个主机（规范化后精确相等），不覆盖同一条通配规则下的其他主机。「只读」= 该主机按只读策略判，所以 `open` 返回的 `mode` 是 `readonly`；「可写」= 只读策略加 `open --allow` 的清单作为放行声明（写策略第 ⑥ 步，mutation 仍要带 `operation`，清单外的写照样被拦）。`open --allow` 只用在 deny 主机上（别处是 usage，只读主机请用 `step --allow`）；`open --readonly --allow` 时框里不列清单、不给「可写」。一次 `open` 同时要过多道闸（规则待批、deny 主机、借用含 deny 的组）时次序固定、全部同步（在 `openSession` 的第一个 `await` 之前），各弹一次框，全部批准后才一起用掉答复，所以人点完后原样重试一次走通，不会出现批准了 A、重试时 A 又被问的循环。**借用**：`--profile` 借用的组里有 deny 主机时弹 `e2k：借用登录`（「拒绝」（默认）/「允许」）；授权只让被借组的 deny 主机作为子请求的目标按只读判，不放行到它们的顶层导航。**记录**：deny 的事实记在 `start.deny`（人批准的主机、模式和清单）、`start.borrowDeny`、`frozen.denied`、`deniedNavigations`、`writes.blocked[*].reason = 'denied'`；报告里单列「不允许的域名」。
- **M3 的落实（不允许模式：和上面设计原文不同的裁定）**：(1) **登录前的模式框改成两步，人在登录前也能选「不允许」**（R1，用户决定，推翻了原先「仍是三键」的裁定）：macOS 对话框最多三个按钮，所以分两步。第一步 `e2k：在新域名上登录`：`不登录`（默认）/ `默认` / `更严…`；`默认` 一步写完，`更严…` 什么都不写、进第二步。第二步 `e2k：在新域名上登录（更严的模式）`（键 `login-strict:` 加规范化主机和 profile，框里显示 profile，kind 仍是 login）：`不登录`（默认）/ `只读` / `不允许`，答完写 `hostModes`。第二步被拒，和第一步被拒同样是 usage，第一步的答复留着，所以内核重启前这个主机重试会直接走到第二步、仍是被拒。选「不允许」的这一次点击就算 R5 的那次批准：这次 `login` 不再弹「在不允许的域名上登录」框，窗口里 deny 照旧按只读算；下一次 `login` 这个主机照 R5 每次弹框，`open`、借用也都走 deny 的闸。WebSocket 维持不拦（见下，文档写明）。(2) **会话页顶层导航进没授权的 deny 主机是中止（abort），不是 403 页，也不是「会话停下」**（R4、R4a）：回一张 403 页面会提交在 deny 的源上，页面里的脚本能读写那个源的 cookie 和存储，所以主页面和能认出归属的弹窗发往没授权的 deny 主机的顶层导航一律 abort，页面不会落在 deny 的源上（停在原来的页，或浏览器的错误页）；`goto` 因此是动作失败（11）；记 `denied`、`deniedNavigations` 加一，下一次 `step` 的 `notices` 带「这个域名是「不允许」的，没经批准不能打开」；子资源仍回 403 JSON（`{"error":"blocked by e2k: host not allowed"}`）；会话不停。经重定向进去（首跳之后的跳，或兜底的地址证据）才冻结会话，复用 M2b 的冻结机制，但**不清 cookie**（那个主机可能本来就属于这个 profile 的组）；deny 冻结的会话里所有导航（含未归属的）一律 abort；别组冻结的会话里，进 deny 主机的子 frame 导航和进已授权 deny 主机的顶层导航回 403 HTML（见已知缺口）；被冻结的会话只能关掉重开（`step` 退出 22）。(3) **发往没授权的 deny 主机的请求一律拦（限经过路由回调的，见下面「覆盖不到的」），推翻上面「默认页面发往不允许域名的写不拦、只记录」**（R18）：任何会话页（含 iframe、子资源、未归属请求）发往没授权的 deny 主机的请求，只要经过路由回调（请求自己的地址、即重定向链的首跳在 deny 主机上），不分方法一律 403、原因 `denied`；授权覆盖的目标按只读判。**覆盖不到的**（终审 F1，写进 reference 的已知缺口）：重定向的后续跳不进路由回调——子资源首跳在别的主机、经 3xx 进 deny 主机会送达（含 307/308 带体重发的 POST）；iframe 经重定向进 deny 主机会把文档提交在 deny 源上，会话也不冻结；只有主 frame（主页面和能认出归属的弹窗）的后续跳会被上报、冻结会话（跳已发出）。WebSocket 不拦：握手不经 `context.route`，驱动只计数；试过 Playwright 的 `routeWebSocket`，它靠往页面注入脚本替换 `WebSocket` 构造函数、并给页面暴露一个绑定函数来实现，页面能自己调这个绑定（伪造的调用会到达驱动的回调）、专用 Worker 里的 `WebSocket` 绕得过去、页面看到的 `WebSocket` 也不再是原生的，违反 5.10「驱动不得往页面里暴露任何能调回驱动或内核的函数」，所以没用。理由：否则 agent 在任意默认页 `eval` 一个 `fetch` 或建一个 iframe，就能不经人点击写 deny 主机，正是反目标「自己打开不允许的域名」；代价是本地页面合法地调用 deny 主机的接口会被拦，要人用借用或改规则。登录窗口不受这条影响。(4) **在 deny 主机上 `login` 也要人点框**（R5）：agent 也能发 `login.begin`，所以先弹 `e2k：在不允许的域名上登录`（「拒绝」（默认）/「登录」，每次都问、不记住）；窗口里能归属到登录窗口的请求，deny 按只读算，不冻结、不 403；但登录窗口开出的弹窗的第一个导航驱动认不出归属，走未归属路径，去 deny 主机的照样中止（已知缺口）。(5) **deny 框的默认按钮是「拒绝」**（R19，见 5.4）。(6) **弹窗首导航**：授权过的 deny 会话里，页面打开的弹窗或 `target=_blank` 的第一个导航驱动认不出归属，走未归属路径，发往 deny 主机的一律被拦（即使是授权的那个主机）：失败关闭，写进 reference 的已知缺口，不放行。(7) **页面所在的主机中途变成 deny**（终审 F2）：会话主页面的顶层主机解析为 deny 且不被授权覆盖时（规则改严，待批的新增 deny 条目立刻生效），`step` 在身份探针之后、放行声明的批准之前抛 `needs-human`（22）「页面所在的域名现在是「不允许」，这次没有执行任何操作」，下一步「关掉会话」，一个操作都不执行、不弹声明框。(8) **待批的收紧只活在 `rules.json` 里**（终审 F3）：待批文件仍存在且能解析时才按「更严合并」生效；文件被删或改坏，未批准的 deny、只读条目立刻失效，只剩已批准的。

### 5.3 写策略

**位置**：放在网络层，用驱动提供的请求拦截（Playwright 是 `browserContext.route()`）。理由：页面里的任何脚本、agent 注入的脚本发出的写都过这一层。若实测发现跨进程 iframe 或原生表单提交拦不住，退回两层：网络层加一段在页面脚本之前注入的页面内拦截脚本（改写 `fetch`、XHR、`sendBeacon`）。

**规则**（顶层页面处于「只读」模式时；「不允许」的域名经批准以只读方式打开时也一样）：

1. `GET`、`HEAD`、`OPTIONS` 放行。
2. `POST`、`PUT`、`PATCH`、`DELETE` 默认拦：给页面回一个假的失败响应，并记进报告。
3. **读型 POST 白名单**，按域名组配置：换 token 的请求（拦了会把整个 profile 登出）、GraphQL 查询、搜索类接口。
4. GraphQL 按 operation 判：查询放行，mutation 拦；放行声明细到 operation 名。只带 hash 的持久化查询要能识别。
5. 登出导航拦下，记进报告。
6. Service Worker 一律 `block`。
7. 页面发往其他域名的请求（监控、埋点、第三方 iframe）同样按这套规则：读放行，写拦下并记进报告；确有需要的可以声明放行。
8. WebSocket：v1 不拦，报告里注明「有 WebSocket 连接，不受写策略管」（拦了页面多半坏掉，先如实标出）。

**M2a 的口径（`write-policy.ts`、`sessions.ts`）**：只读模式只放行读（`GET`、`HEAD`、`OPTIONS`，不带请求体）和严格的 GraphQL query：方法 `POST`、`Content-Type` 为 `application/json` 或 `application/graphql`、URL 上没有 `query` 参数、每个操作都是带选择集的 `query`。严格 query 放行时不跟重定向（驱动在首跳 3xx 中止，那条写记成被拦的 `redirected-write`）。还没有读型 POST 白名单和放行声明，持久化查询（只带 hash）一律拦。`GET`、`HEAD` 的 URL `query` 参数是 mutation，或判不出但含 `mutation` 一词，也拦。拿不准的、判断出错的一律拦（失败关闭）。拦下的请求不管方法都进记录，原因（`method`、`graphql-mutation`、`persisted-query`、`redirected-write`、`unattributed`，外加跨组导航的 `other-group`）和判定当时的有效模式一起记下。给页面的回应：子资源请求回 `403` 加 JSON `{"error":"blocked by e2k read-only mode"}`（跨源时页面上表现为 CORS 错误），导航回一张写着同一句话的 `403` 页面。`step` 的结果带 `writesBlocked`（本批执行期间被拦下的本会话请求数；执行结束后才到的「重定向被拒」算进下一批，未归属的不算）和 `notices`，退出码不变。

**M2b 的落实（组级白名单，`write-policy.ts`、`graphql.ts`、`sessions.ts`）**：只读模式的判定顺序是固定的，顺序就是语义：① 命中 `logout`（任何方法）→ 拦，原因 `logout`，先于一切；登出按路径匹配，忽略查询串和 fragment、结尾单个 `/` 等同（拦截名单窄了是漏拦，所以不像放行名单那样要求精确）；② 安全方法无体 → 照 M2a；③ 判出 mutation（`graphqlKind` 是 `mutation`，或 URL 像 mutation）→ 只有带 `operation` 的放行声明命中（每个操作的 `operationName` 都等于它）才放行，否则拦 `graphql-mutation`，所以 mutation 排在所有白名单之前；④ 命中 `readPosts`、体不像 GraphQL（有 `query` 键，不分大小写、不管值的类型；`extensions` 里有 `persistedQuery` 键；`application/graphql`；体到了 64 KB 可能被截断；长得像 JSON 却解析不了；GraphQL 的 multipart 上传）、且 `graphqlKind` 为 null（`unknown` 也不行：拿不准是不是 GraphQL 就当它是）→ 放行，`allowedBy: 'read-post'`；⑤ 持久化查询：方法 `POST`、`application/json`、体不到 64 KB、没有重复的键（任何对象里，转义解码后比）、单个或数组，每一项的键只在 `operationName`、`variables`、`extensions` 里，`extensions` 只有 `persistedQuery`，它只有 `version`（数字）和 `sha256Hash`（64 位十六进制，转小写），URL 命中某个 `persistedQueries` 接口、全部哈希在这个接口的清单里 → 放行，`allowedBy: 'persisted-query'`；⑥ 命中放行声明 → 放行，`allowedBy: 'declared'`（只带哈希的持久化查询不被任何声明覆盖，带不带 `operation` 都一样：文档看不到，`operationName` 是客户端自报的，它只能由 `persistedQueries` 白名单放行）；⑦ M2a 其余（持久化查询拦、严格 query 放行、其余拦 `method`）。所有白名单放行都带 `followRedirects: false`（驱动只对同源请求做到，跨源的见 docs/reference.md Known M1 gaps）；默认模式全放行，`denied` 照旧中止。内核按请求组装清单，策略不认识组：`logout` = 会话所在组的 ∪ 请求目标主机所在组的（登出主机可能是组的 `loginHosts`，不在 `hosts` 里，所以要并上会话组）；`readPosts`、`persistedQueries` 只取目标主机所在组的（接口的主机必须在组内，规则解析期保证）；冻结、跨组导航的检查都在它们之前。四条请求路径：会话页和会话弹窗按上面判；登录窗口（含弹窗）里 `logout` 传空（允许登出，好换账号）、`declared` 传空，读型 POST 和持久化查询照目标主机所在的组；未归属的请求（`decideUnattributed`）不放行任何白名单里的写，只在有只读会话或所在页只读时，拦所有已批准组的 `logout` 的并集、写、带体的安全方法和 URL 像 mutation 的 GET/HEAD（`ModeResolver.allLogout()`；`groupOf` 看不到写在 `loginHosts` 上的登出，也不知道未归属的请求该算哪个组，多拦即失败关闭）。报告：被放行的写带 `allowedBy`（只在靠白名单放行时才有这个键），被拦的 `logout` 是新的拦截原因。

**放行声明**：`{ 方法, URL 模式, GraphQL operation 名（可选） }` 的列表，挂在一次会话或一个用例上。声明只是「请求」，生效以内核里的批准记录为准（见 5.4）。

**留痕**：报告里单列「这次动了什么」，逐条列出放行的写（方法、URL、时间、状态码，请求体脱敏后截断）。发出请求的页面（或其顶层文档）有密码类输入框、或判断不出时，只记方法、URL、状态，请求体不记（`bodyOmitted`，失败关闭）。报告在写请求段开头还有一张汇总表，按主机 × 方法分组，列放行和拦下的个数（只有主机名，不带路径和请求体；未归属的写不计入）；GraphQL 的写再分 query、mutation、subscription、unknown（`result.json` 的 `writes.summary`、各条写的 `graphql`），这只是给人读的分组，拦不拦由严格 query 检查定（见 M2a 的口径），拿不准的（持久化查询、被截断的请求体、括号不平衡的文档）一律是 unknown，不算 query。

### 5.4 批准

需要人批准的四件事：

| 事 | 何时问 | 记不记住 |
|---|---|---|
| 改域名规则、域名组、读型 POST 白名单 | 每次改动 | 记住，绑定配置内容；内容变了重新问 |
| 在「只读」域名上放行一组写 | 第一次用这组声明时 | 记住。同一域名下，已批准过的声明及其子集不再问；多出新的一条就只问新的 |
| 打开「不允许」的域名 | 每次运行 | 不记住。每次都问，默认按钮是「拒绝」（见下面 R19）；选「可写」要同时确认放行清单 |
| 借用含「不允许」域名的组的 profile | 每次运行 | 不记住。只问是否允许 |

- **M3 的落实（不允许类的批准，`sessions.ts`）**：上表里和 deny 有关的四样各有自己的框和待批键：打开（`deny:`，`e2k：打开不允许的域名`，「拒绝」（默认）/「只读」/「可写」）、借用含 deny 的组（`borrow:`，`e2k：借用登录`，「拒绝」（默认）/「允许」）、在 deny 主机上登录（`deny-login:`，`e2k：在不允许的域名上登录`，「拒绝」（默认）/「登录」）、目标或页面主机是 deny 的放行声明（`deny-writes:`，`e2k：放行写请求`）。键都绑定框里显示的全部内容（会话名、profile、主机、`--readonly` 与否、清单）。**默认按钮是「拒绝」**（R19）：上表原写「默认只读」，但下面的硬约束要求批准框的默认按钮是拒绝一类（`approval.ts` 把 -128 映射成「按了默认按钮」靠的就是它），取硬约束，人要多点一下「只读」。**有效期**（R20）：这几类批准后 5 分钟内没被用掉就作废，下一次重试重新问；会话 `close` 时作废本会话的 `deny-writes:` 答复；一次 `open` 的多道闸全部批准后才一起用掉答复，否则前面已批准的答复会在后面的闸被拒时一直留着，几小时后同参数的 `open` 不用点就过闸，违反「每次运行」。**deny 主机的放行声明只活在会话里**（R21）：目标主机（声明地址的主机）是 deny、或会话页面主机是 deny 的声明，每次都问、不进批准记录，存成「页面主机加声明」绑定在会话上，页面搬走就不再生效；批准记录里记住过的、目标是 deny 主机的声明判定时一律不用。**借用的落实**（R2）：授权只让被借组的 deny 主机作为子请求的目标按只读判，不放行到它们的顶层导航，顶层导航只认 `open` 授权的那一个主机。
- **放行声明可以在会话中途追加**：agent 往往要等写被拦下才知道该声明什么。`step` 带上新声明 → 内核返回「等人批准」→ 批准后同一会话接着跑，页面状态保留。
- **「一次运行」**指一个会话或一次 `run`。并行开第二个会话要再问一次。
- **「不允许」域名上的放行清单由 agent 在 `open` 时声明**，人在确认框里只做选择：拒绝、只读（声明整体不放行）、可写（只放行清单里的）。会话中途追加声明就再弹一次确认框。
- `open` 阶段等批准时还没有会话：内核给这次请求一个请求 id，确认框里显示它，agent 重试时带上。（M2b 落实时改了：重试**原样**重试、不带 id，内核按内容键（规则的基线+待批哈希、声明的会话名/组/页面主机/声明集合、登录的主机）把重试和已点过的框对上；id 只用来让人把终端上的提示和弹出的框对照起来。）

流程：

1. agent 的调用需要批准时，内核返回「等人批准」加一段给人看的摘要（域名、模式、要放行的写）。这是可恢复的阻断，不是失败。
2. 内核自己向人发起确认（v1 用 macOS 原生对话框，由内核进程弹出）。
3. 人确认或拒绝后，agent 重试原调用即可继续。

硬约束：

- **批准不能经由 CLI 或 MCP 的协议完成**。没有 `approve` 子命令，没有对应的 MCP 工具。
- **弹框的实现（M2b）**：对话框实现注入内核（`startKernel` 的 `dialog`），测试用假实现，`e2k start --no-dialogs` 换成永远弹不出的实现，只会让结果更严（22）。真实现用 `osascript`，正文、标题、按钮名一律经 argv 传入，不拼进脚本；输出只认去掉一个末尾换行后的精确形状，其余（非 0 退出、被杀、多出的输出、不在按钮里的名字）按弹不出处理，唯一的例外是人取消（`osascript` 退出时 stderr 为 `User canceled. (-128)`，被杀的不算；终审 I-3）：按「按了默认按钮」算（所有批准框的默认按钮都是拒绝或不登录一类；真机实测按 Esc 对批准框没有作用，框会留着直到点按钮或 120 秒超时，所以这条 -128 映射只是兜底），不标坏、之后还能再弹框；不在图形登录会话里（`launchctl managername` 不是 `Aqua`）一直弹不出。`doctor` 用同一个取法报「批准对话框」一项：不是 `Aqua`（或取不到）提示「弹不出批准框，需要批准的操作会返回 22」，只是提示，不让 doctor 的退出码变失败，也从不弹框、不调 `osascript`。待批表同步返回，框在后台弹：同一时刻屏幕上最多一个框，其余排队；同一类被拒后 60 秒内直接拒，同一个请求被拒后内核重启前不再问；10 分钟内弹过 6 个框就不再弹（22）；弹不出框之后这个内核里的后续请求一律 22。对话框里显示原值，不脱敏不截断，任一行超过 200 字符或正文超过 1500 字符就直接拒绝这次请求。
- 批准记录存在内核的状态目录里，不存在用例文件里。用例文件 agent 可以改，所以它只能表达「请求」。
- **M2b 的落实：规则的批准快照（`approval-store.ts`、`rules.ts`、`mode.ts`）**：改规则一律要批准，含收紧、删文件；生效的是批准快照，不是磁盘上的 `rules.json`。批准记录 `$E2K_HOME/approvals.json`（0600、只由内核写）在内核启动时读一次，之后以内存里的为准；`update` 先写同目录随机名临时文件（`O_CREAT|O_EXCL|O_NOFOLLOW`）再 `rename`，成功了才换内存，序列化后超过 2 MB 或写不进去就抛错、内存不变。读时按「不信任」读（`O_NOFOLLOW|O_NONBLOCK`、普通文件、不超过 2 MB、形状严格），符号链接、FIFO、目录、超大、坏 JSON、多余键都算读不了：当没批准过，现有规则全部重新批准。**运行中磁盘上的文件被改、被删、换成符号链接都不让内存里的批准降级**，`externallyChanged()` 每次 `refresh` 比一次磁盘（只比哈希、从不把磁盘内容读回内存），结果只进 `status` 的提示。`refresh` 把 `rules.json` 的原文和快照原文比：一样 = 无待批；不一样且解析得了 = 待批（原文和哈希留在内存里）；改坏 = `error`（坏文件不进待批）；文件不存在而快照里有规则 = 待批的「删文件」。**待批期间的模式取已批准和待批文件里更严的那份**（取并时 `denied` > `readonly` > `default`，所以只有 `rules` 里新增或改严（只读、不允许）的条目立刻生效、放宽等批准；待批是删文件则只看已批准的）；组、白名单、`loginHosts`、`logout`、`identity` 只认已批准的：它们的改动哪怕是收紧也要等批准（终审 I-4：提示、规则框、agent-guide、README 曾写成「收紧已生效」，说多了）。待批的身份是原文的完整 sha256（64 位十六进制，`ModeResolver.pending().hash`），`approvePending(hash)` 比的是它，不是 16 位短哈希；`status`、报告和批准记录里存的、显示的仍是短哈希（64 位十六进制过脱敏会被抹掉）；同一组里同一个接口只能写一条 `persistedQueries`（否则差异按接口合并会漏掉新哈希，解析即报错）；批准写盘成功后 `state().approvals` 置为 `ok`。`approvePending(hash)` 只在内存里待批的哈希等于 `hash` 时，把内存里那份原文写进批准记录并生效，不重读磁盘，传旧哈希得到 false（调用方重新 `refresh`）。待批的说明 `summary` 把待批内容和已批准内容逐字段比较，放宽的排前面（读型 POST、持久化查询和新哈希、登录主机、登出被删、身份探针、主机换组、只读规则被删或改成默认），收紧的在后面；`tooLong` 按字符判（终审 M-1，原先按 12 行，首次配几个组几乎必然超）：差异（行间一个换行）超过 1300 字符，或任一行超过 200 字符（弹框限制是每行 200、正文 1500，差异给首尾框架文字留 200 字符的余量），入口闸门的弹框据此只给「拒绝」；框架文字加上差异万一仍超出弹框限制，闸门也走这条路，不从 `approvals.ask` 抛「内容太长」。`rule diff` 打印同一份完整差异，`rule list` 注明每条规则是否在快照里，`doctor` 的规则一项报「已批准 / 有未批准的改动 / 批准记录读不了」。**入口闸门（`sessions.ts` 的 `gateRules`）**：`openSession`、`beginLogin` 在规则文件有错的检查之后、做任何别的事之前先看 `pending()`；非 null 就用内容键 `rules:<已批准快照的完整哈希，没有为 none>:<待批的完整哈希，删文件为 deleted>`（`PendingRules.baseHash` 和 `hash`）向 `Approvals` 问一次；键里带基线，所以没用掉的旧批准在别的批准落盘、基线变了之后对不上新的请求（改回早先批准过的文本必须重新问），`approvePending` 成功后还把 `Approvals` 里其余已批准的 `rules:` 键一并作废（`forgetApproved`，被拒的保留）：标题「e2k：域名规则改了」，正文是短哈希加 `summary`（放宽的在前），按钮「拒绝」（默认）、「批准」，120 秒。`pending` → 21；`denied` → `usage`（冷却中是另一句）；`unavailable` → `needs-human`（22）；`approved` → 用**内存里待批的完整哈希**调 `approvePending`（不重读文件），成功就 `forget(key)` 继续，返回 false（同步调用之间不可能，只会是内核自己的 bug）抛 `internal`、不放行，`approvePending` 写盘失败抛的 `needs-human` 原样往上。`tooLong` 的框只有「拒绝」、`approveButtons` 为空，必然 `denied`。待批期间所有新的 `open`、`login`（含 `open --readonly`）都先过它，所以没有绕过的入口；收紧在批准前已按「更严合并」让已开会话的下一个请求生效。`step` 的 `notices` 在有待批时加「规则文件有未批准的改动（只有新增或改严（只读、不允许）的规则条目已先生效，其余改动要等批准）」，`approvalsChanged` 为真时加「批准记录被内核以外的进程改过，已忽略」。启动时批准记录读不了且 `rules.json` 存在：快照为空，文件自然进待批，`status`、`doctor` 报「批准记录读不了」。
- **M2b 的落实：放行声明的批准（`declarations.ts`、`sessions.ts` 的 `gateDeclarations`、`declaredFor`）**：声明只在 `step` 上提（`--allow <JSON>`，协议 `StepParams.allow`，最多 12 条，协议层只查形状和长度），内核规范化：方法只收 `POST`/`PUT`/`PATCH`/`DELETE`，地址照接口写法（不带查询串，规范化成 `origin/路径`），`operation` 匹配 `^[_A-Za-z][_0-9A-Za-z]{0,99}$`，去重、排序；不合格是 `usage`，不弹框。`step` 在执行任何操作之前先过这道闸：批准记录里已有的（规范化后全等；记录按 `组/页面主机` 存，页面主机是会话主页面已确认的顶层主机）不再问，其余的（不管目标主机是什么模式）弹一个框 `e2k：放行写请求`，正文是会话名、组、页面主机、每条 `方法 地址` 加说明（带 `operation` 的写「只放行 operation 名」，不带的写「这个地址上的所有写；GraphQL mutation 不在内」），按钮「拒绝」（默认）、「放行」，120 秒。待批表的键是 `writes:` 加 sha256（会话名、组、页面主机、待批声明排序后的 JSON）：答复绑定框里显示的全部内容，页面搬了主机、声明多了或少了、换了会话，旧答复都对不上，重新弹框；批准用掉（写进批准记录、`forget`）之后，同类里别的已批准但没用掉的键一并作废（`forgetApproved`）。被拒的集合另记一份不带会话名的键（`deniedWrites`，内核重启前有效）：换会话也不重新弹框；同类 60 秒冷却是待批表自己的。`pending` → 21 且不执行任何操作，`denied` → `usage`，`unavailable` → 22；整个调用全有或全无：没批准的这一批什么都不记进会话。会话记 `declared`（提过且已批准的，带批准时的 `组/页面主机` 和是弹框批准还是沿用），判定用的声明 = 会话的 `declared` ∩ 批准记录里现在的内容，且要和会话现在的组、页面主机一致（判定时再核对：记录里没了、页面搬了主机都失效）。**不改写策略的判定顺序**（① 登出 ② 安全方法 ③ mutation 只认带 `operation` 的声明 ④ 读型 POST ⑤ 持久化查询白名单 ⑥ 声明 ⑦ M2a 其余）；只带哈希的持久化查询（含 `query` 为空串或全空白的）不被任何声明覆盖。**四条请求路径**：会话页、认得出归属的会话弹窗用 `declaredFor`；弹窗的第一个导航（驱动认不出归属）和未归属的请求走 `decideUnattributed`，没有声明，失败关闭；登录页（含弹窗）`declared` 传空。`result.json` 有 `declarations`（`method`、`url`、`operation`、`approved`），报告里单列「放行声明」。
- **威胁模型**：防的是 agent 走偏、误操作、图省事绕路，不防蓄意攻击的 agent。同一系统用户下的 agent 理论上能改状态目录或操控桌面，v1 不做签名之类的加固，在文档里如实写明。具体到批准：`approvals.json` 只由内核写，同一用户下的 agent 理论上能改它（内核只报提示，运行中仍以内存里的批准为准）；终端有「辅助功能」权限时，agent 能用自动化点掉批准框，这一层保护等于没有，所以不得用任何自动化去操作批准框。

### 5.5 登录和 profile

- 一个 `default` profile，加每个域名组一个 profile。每个 profile 一个 user data 目录，放在内核状态目录下，目录权限只给当前用户。
- 每个 profile 同一时刻一个 Chromium 实例；多个会话是这个实例里的多个标签页。
- `login <URL 或组名>`：内核打开对应的 profile，人在里面登录。配了登录页识别规则就按它判断登录完成，没配就由人在终端里按回车确认。
- **登录窗口里的写照只读规则拦，只有两类免拦**（M2a）：`login` 打开的窗口（含它弹出的窗口）里，(1) 请求目标主机在 `loginHosts` 里，或 (2) 是表单提交（顶层导航）且发起它的页在 `loginHosts` 的主机上（发起页的地址以驱动给的 `initiatorUrl` 为准，没有才用跟踪到的已提交/待定主机；`initiatorUrl` 是被导航替换的那份文档，iframe 的 `target=_top` 等少数导航里它不是真正的发送者）——这是 SAML POST 绑定、OIDC `form_post` 回调从身份提供方回到应用的路径。所以要把身份提供方的主机列进 `loginHosts`，回调由此自动放行，接收回调的应用主机不用列。其余一律不免：`loginHost` 页上的 fetch/XHR 写别的主机照只读规则判；托管在只读主机自己上的用户名密码表单，除非该主机也列进 `loginHosts`，否则会被拦（已知取舍）。登录页在哪个主机上，照会话主页面那套跟（起始主机、放行的导航目标作待定、非导航请求带的顶层地址作已提交的证据，顶层导航带的 `initiatorUrl`（被导航替换的那份文档的地址，通常就是发起页）是更直接的证据，先据此定下导航前页面的主机再判断——经重定向进入身份提供方、且它的自动提交页没发过别的请求时，只有这一条能认出发起页）；身份提供方页自己写的第三方主机（验证码、内嵌的 MFA 验证框、遥测）在登录起点只读时也要列进 `loginHosts`；把只读的应用主机本身列进 `loginHosts` 的代价是：登录窗口发给它的写全部免拦、也不记录；弹窗在拿到证据前按开启者已提交的主机算。不免拦的请求，有效模式取并：登录起点主机只读、页面的已提交或待定主机只读、请求自己的顶层主机只读，任一成立就按只读，走和会话相同的写策略（严格 query 照样放行且不跟随重定向）。登录请求不进任何会话记录；被拦的只在内核日志留一行（登录 id、方法、脱敏主机，不写路径和体），并累计进 `login.end` 的 `writesBlocked`，CLI 收尾时据此提示检查 `loginHosts`。`login.begin` 先刷新规则，文件有错时和 `open` 一样被拒。`login.begin` 本身仍是本机任何客户端都能发的（威胁模型已写明），登录前的弹框确认见下一条（M2b 已落实）。会话处于「等登录」时，人在会话窗口里登录也按该会话的模式拦：要登录请用 `login`。
- **M2b 的落实：登录前的弹框确认（`sessions.ts` 的 `gateLoginHost`、`mode.ts` 的 `isListed`、`approval-store.ts` 的 `hostModes`）**：`beginLogin` 在规则闸门之后、选完 profile 之后、启动实例和算 `login.mode` 之前，先问这个主机「列明」了没有：命中已批准的规则、在 `hostModes`（登录时选过）里、属于某个组（`hosts`）、或在任何组（含顶层）的 `loginHosts` 里才算列明；待批的规则不算，规范化出错算没列明（多问，失败关闭的方向）。没列明就弹两步框。第一步 `e2k：在新域名上登录`：`不登录` / `默认` / `更严…`，默认按钮是「不登录」（终审 I-3：不叫「取消」，免得被 `osascript` 当成系统取消键），120 秒，框里只有规范化后的主机（小写、去端口、去结尾点、punycode）和选项；答「更严…」进第二步 `e2k：在新域名上登录（更严的模式）`：`不登录` / `只读` / `不允许`（M3，R1）；规范化不了的主机（含取不到主机）、`__proto__`、正文行超过 200 字符的，直接 `usage`，不弹框。待批表的键是 `login:`（第二步 `login-strict:`）加规范化主机，已经绑定了框里的全部内容；各主机的键彼此独立，没有「基线」会变，所以用掉之后只 `forget` 自己的两个键（不调 `forgetApproved`），主机后来被规则列明时没用掉的旧答复也被丢掉；被拒的保留到内核重启，同类 60 秒冷却。答「默认」（第一步）、「只读」「不允许」（第二步）→ `store.update` 把 `hostModes[host]` 写进批准记录（不改 `rules.json`）、`forget` 两步的键再继续，两步都在同一个同步段里、第一个 `await` 之前；写盘失败 → `needs-human`（22），答复保留，重试再写；答「不登录」→ `usage`「人取消了这次登录」，窗口不开；弹不出框（`--no-dialogs`、没有桌面、额度用完）→ 22，绝不放行。`resolve(host)` 先看规则（含待批期间「更严合并」），规则没命中才看 `hostModes`（精确主机，不通配）：它只管没列明的主机，压不过任何已批准的规则，待批里的放宽也抬不高已选的「只读」。会话页、会话弹窗、登录页（含弹窗）、未归属请求四条路径的判定都经 `resolve`，所以选了「只读」之后，这个登录窗口自己的写、之后开这个主机的会话、顶层在这个主机上的弹窗和未归属请求都按只读拦；模式跟着页面走这一点和规则一样（默认主机上的页面发往只读主机的写不拦，只记录）。模式时间线的 `reason` 为 `host-choice`。CLI `login` 收到 21 每 2 秒原样重试，每换一个请求 id（两步框是两个 id）重新计 120 秒并打印一次 `请在弹出的对话框里选择（请求 <id>）`（同一个 id 等满 120 秒打印「对话框超时，请重新运行 login」，退出码 21）；`rule list` 列出 `hostModes` 和记住的放行声明（CLI 自己读状态文件，只读）。`hostModes` 的条目只增不删，每条都经过人点一次，条数受每 10 分钟 6 个框和 2 MB 的记录上限约束。
- 会话中发现掉线：返回「等登录」（可恢复的阻断，和失败用不同的退出码），人在同一个浏览器窗口里登好后，agent 重试即可在原页面续跑。
- **v1 一律有头运行**，窗口不抢焦点。理由：一个 profile 只有一个实例，实例启动后不能在有头和无头之间切换，而登录必须有头；一律有头就不用为了登录重启实例、丢掉其他会话的页面。顺带让过程可见。无头留到以后做 CI 时再加。
- 用 Playwright 自带的 Chromium，不碰用户的日常浏览器。
- **浏览器 provider（M4）**：缺省仍是 Playwright 自带的 Chromium。人在 `e2k start` / `e2k doctor` 时可以用 `--browser <预置>`（`ego-lite`、`playwright-chromium`）或 `--browser-path <绝对路径>`（也可用环境变量 `E2K_BROWSER`、`E2K_BROWSER_PATH`；命令行优先）换成另一个 Chromium 内核浏览器；协议、MCP、`open`/`step` 里没有这个选项，会话里不能换。启动方式不变：自己 spawn、管道、专用 profile、不开调试端口，写策略一行不改。`start` 没有终端检查，所以 agent 起内核时也能给路径，靠留痕（报告、`status`、`doctor` 写明浏览器和版本，自定义的标成「自定义浏览器」），与威胁模型一致。路径检查（`providers.ts` 的 `checkExecutable`）：绝对路径；真实路径是可执行的普通文件；属主是当前用户或 root；文件和它所在的目录都不是 world-writable（组可写放行：macOS 上用户自己装的应用常带 g+w，同一用户的进程本来就能改它）；报错不回显路径。非缺省 provider 还有两道保护：(1) 启动后先做**拦截一致性自检**——对一个不存在的 https 主机，路由对子资源生效、Service Worker 注册被禁、`SharedWorker` 被删，任一不符 `launch` 失败（不开任何会话）；(2) **profile 绑定**：第一次启动在 `profiles/<名>.browser.json` 记下 provider，之后换 provider 一律 22（没有记录但目录用过的，当作 `playwright-chromium`；记录读不了也 22），不自动迁移、不自动删。ego lite 的特殊处理（实测，`docs/m0-findings.md` §11）：它不遵守 `--no-startup-window`、启动抢一次前台、自带首次引导页，所以焦点管家按它的 bundle id（从 `.app` 的 `Info.plist` 读）认「前台是不是 e2k 的浏览器」，启动后自动关掉引导页（`chrome://onboarding/`）并多等 1.5 秒再开页；它还不理 `Browser.close`、管道一断就退出，最近 30 秒内写的 cookie 会丢，所以停止前先关掉还开着的页再等 0.5 秒（`flushOnPageClose`）。
- **profile 状态和最近一次 login**：`status` 和 `doctor` 报 profile 的状态（`missing` / `never-launched` / `launched`，只表示浏览器有没有用过这个目录）和最近一次 `login` 的时间与主机。记录在 `profiles/<名字>.login.json`（0600、不跟符号链接，放在 profile 目录旁边而不是 user data 目录里，不会被浏览器或页面碰到），只在人按回车结束 `login` 时写；写失败只记日志。判断有没有登录态看这条记录，不看状态：会话窗口里手动登录不会记。`doctor` 只读，没 login 过不算失败，也不会让退出码变成 22。
- **M2b 的落实：每个 profile 一个实例（`profiles.ts`、`sessions.ts`）**：profile 的 key 是 `组` 或 `组@槽`（命令行写 `组/槽`，`parseProfileArg`、`profileKey`），两段都只收小写 `^[a-z0-9_-]{1,32}$`，key 同时是 `profiles/` 下的目录名，所以名字里没有 `.`、`/`、`..`、大写，逃不出 `profiles/`；`default` 的目录名不变。`SessionManager` 的实例表是 `Map<key, { instance?, acquiring? }>`，`acquireInstance(key)` 按 key 懒启动，同一个 key 并发启动只 `launch` 一次。启动前由 `prepareProfileDir` 做完所有检查，不对就不启动浏览器：key 不合规 → `usage`；`profiles/` 和 profile 目录不存在就建成 0700，已存在的必须是真目录、属于当前用户、组和其他人没有权限位；profile 目录是符号链接（含悬空的）、普通文件 → `needs-human`（`profile 目录不对`）；`resolveInside` 再按真实路径确认严格在 `profiles/` 之内。同时在跑（含正在启动、正在被回收）的实例最多 4 个，非法 key 先于上限判断被拒（不占槽）。要启动的 key 已满员时先回收空闲实例：没有会话、没有登录页、没有正在开会话或登录页的调用（`pin`/`unpin` 钉住）、不在启动中的实例算空闲，停最久没用的那个（按「最后一个会话或登录页结束」的单调序号；不在最后一个会话关掉时立刻停，免得每次重开都要重启浏览器、多抢一次焦点），一个空闲的都没有才 `busy`。判断、挑选、摘掉实例、给新槽占位都在 `pin` 的同一个同步段里，所以并发的请求越不过上限；被回收的实例摘掉后还占着名额，停完才放，新 key 在它停完（`slot.after`）之后才启动，所以同时活着的浏览器从不超过 4 个；回收期间又来了被回收的 key 自己：同样等它停完再重启（也要重新过上限）。登录态在 profile 目录里，回收不丢。启动失败的 key 不占名额（空槽随即摘掉）。profile 目录的检查和浏览器启动之间有短暂的时间窗（同一系统用户的进程可以在这期间把目录换成符号链接），属于威胁模型里「同一系统用户」的范围，不另加固。请求回调、`onRequestDone`、`onPageOpened`、`onClosed` 都挂在各自的实例上；页面 id 和请求 id 在驱动对象生命期内唯一（见驱动协议），所以按 id 找会话或登录页不会串。一个实例没了（`browserGone(inst)`）只收尾这个实例上的会话（各出 `browser-gone` 报告）和登录页，其他实例不受影响；关停等还在启动的实例落定，再把所有实例一起停。`Session.start.profile` 存 key，`Login.profile` 存登录用的 key，`loginEnd` 把登录记录写到对应 profile 名下。`openSession`、`beginLogin` 里 `gateRules()` 仍在规则错误检查之后、`acquireInstance` 之前：闸门先于任何实例启动和开页。`status` 的 `profiles` 用 `listProfiles`：`default` 在前（目录在不在都列），再是 `profiles/` 下名字合规的真目录，按名字排序，符号链接和别的条目跳过且不跟进去；`instance` 字段保留，任一实例在跑就是 `running`；`doctor` 每个 profile 一项检查。`open`、`login.begin` 用 `profile` 选 profile（见 5.2「M2b 的落实（选 profile、借用、跨组导航）」）。未归属的请求（`pageId` 为 null 或人手开的标签页）判「有没有只读会话」时仍看所有实例上的会话（比只看本实例更严，是有意保留的偏保守行为）。
- **M2b 的落实：开会话不抢前台，控制通道是管道（`drivers/playwright/browser-process.ts`、`driver.ts`）**：驱动自己 `spawn` 浏览器可执行文件（`execFile` 式 argv，不经 shell；自成进程组），参数是 Playwright 自己用的那份开关（去掉 Windows、Edge 专属项，不带 `--no-sandbox`）加 `--remote-debugging-pipe --no-startup-window --user-data-dir=<profile>`，绝不带 `--remote-debugging-port`、`--remote-debugging-address` 和启动页。管道（fd 3、4，一条 JSON 后跟一个 NUL）经 Playwright 公开的 `chromium.connectOverCDP(transport)` 重载交给 Playwright，之后一切照旧（路由、事件、截图……）。开页一律是 browser 级 `Target.createTarget`（`createTargetParams`：会话页 `background: true`；登录窗口要人来操作，`openPage({ foreground: true })` 即 `background: false`，终审 I-2），再从 `page` 事件里**确定性地**认领自己开的那一页：起始地址是 `about:blank#e2k-<128 位随机十六进制>`（这次创建专用，不进日志、报告），只认 `url()` 恰好等于它的页——页面脚本不知道这个值，所以别的会话的页开出的窗口（哪怕空白、哪怕开启者已经关了，`opener()` 为 `null`）怎么出现都不会被认走（审阅发现 I1：原先靠「空白 + 无 opener」认领，开启者关了的空白窗口会被认成别的会话的主页面）。认领后马上 `history.replaceState(null, '', 'about:blank')` 把地址改回干净的 `about:blank`（带 `#` 的地址会让第一次导航被 Playwright 当成「换了文档」，主 frame 的快照引用从此带 `f` 前缀、被当成 iframe 引用；`replaceState` 是同文档导航，不动帧序号），并要求页内脚本 5 秒内能跑，不通就 `Target.closeTarget` 关页、报错。不对候选页建 CDP 会话去问 targetId（会和触屏用例的会话计数冲突）。开页期间别的会话新出现的弹窗会先暂存（`deferred`），开页结束才登记；暂存期间它们的请求按未归属处理（见 docs/reference.md Known M1 gaps）。**管道传输必须一条消息一个事件循环任务**（`pipeTransport` 用 `setImmediate` 逐条派发，`onclose` 排在已收到的消息之后）：浏览器一口气发来「响应 + 紧跟的事件」时，若在同一个同步循环里全派发，Playwright 来不及在响应的 promise 续接里登记 frame，紧跟的 `Runtime.executionContextCreated` 就被丢掉，新页的主世界执行上下文随机缺失、页内 `evaluate` 一直挂着（实测：同样的并发开页，WebSocket 传输没事、同步派发的管道传输四个页里挂两三个，改成逐条派发后 30 轮无一挂起；`test/unit/browser-process.test.ts` 守着）。页默认视口 1280x720 在认领之后设。驱动代码里不再出现 `context.newPage()` 和 `launchPersistentContext`（单元测试守着）。**为什么是管道不是调试端口**：127.0.0.1 上的调试端口没有认证，本机任何进程（含同一台机器上的其他系统用户）都能连上、完全控制这个带登录态的浏览器；管道只有内核和这个浏览器进程两端持有，别的进程碰不到，浏览器也只在内核存活时活着。探针数据见 `docs/m0-findings.md` §7.3：管道方案启动和开页都不抢，没有用上调试端口。**进程生命周期**：驱动记着自己 spawn 的那个 pid，关闭只碰它：先 `Browser.close`（让 cookie 等落盘），再关管道，等 3 秒，还在才 `SIGTERM`，再等 3 秒，还在才 `SIGKILL`（连同它自己的进程组）；进程已经退出就一个信号也不发（pid 可能已被别人用掉）；不按名字或目录去找别的浏览器进程，所以不会碰用户自己的、别的会话的浏览器。浏览器意外退出（崩了、被 `kill`、人按了 Cmd-Q）：管道断开、进程退出，实例置为已关，`onClosed` 照旧触发一次（会话的 `browserGone` 语义不变）；内核自己没了（含 `kill -9`），管道断开，浏览器随之退出，不留带登录态的孤儿进程。**连接已有浏览器的默认 context 传不了创建选项**，所以补两处：Service Worker 仍一律禁掉（用 Playwright `serviceWorkers: 'block'` 装的那段初始化脚本，在所有页面所有 frame 里让 `register()` 什么都不做，`coverage.serviceWorkers: "blocked"` 照旧；`test/browser` 里「no service worker gets registered」守着）；页面默认视口 1280x720 在开页时设（原来 `launchPersistentContext` 的默认值）。拦截仍在每个请求上生效，与启动方式无关：路由挂在 context 上，判定逻辑一行没改。
- **M2b 的落实：把焦点还回去（`focus.ts`）**：有头浏览器起窗口、`context.newPage()`、页面自己弹窗都会抢前台（`docs/m0-findings.md` §7.1）；任务 16 之后内核自己起浏览器、自己开页的两步不再抢（见下一条，§7.3），只剩页面自己弹出的窗口会抢，下面的「还」就是为它留的，对 `open` 的启动和开页只是兜底。`FocusKeeper.capture()` 在 `openSession` 启动实例之前、`step` 执行操作之前记下前台应用的 bundle id（`lsappinfo front` → `lsappinfo info -only bundleID <ASN>`，输出按不信任输入解析：ASN 要合 `^ASN:0x…-0x…:$`，id 要整行合 `bundleID="[A-Za-z0-9.-]{1,255}"`，对不上就是 null；前台已是 e2k 的 Chromium（id 含 `chromium` 或 `chrome.for.testing`）也是 null）。`restore(token)` 只在 token 非空、且此刻前台仍是 e2k 的 Chromium 时才 `open -b <token>`（子进程一律 `execFile` + argv、每次 ≤2 秒），用户自己已经切到别的应用就不动；所有失败吞掉、记 kernel.log，不改变 open / step 的结果。`open` 无论成败都在结束时还；`step` 只有本会话新开了页（`onPageOpened` 里按会话计数；step 期间，或 step 结束后 1.5 秒宽限期内）才还，没开新页不碰 `open -b`。**step 之后的还在后台做，step 照常返回**（真机实测，`docs/m0-findings.md` §7.4：弹窗的 `onPageOpened` 事件和浏览器抢前台都晚于 `runOps` 返回，在 step 末尾同步还一次会落空）：`restore(token)` 返回布尔（真的跑了 `open -b` 为 true，哪怕它失败；没动手为 false），`handBackLater` 每 100 ms 一轮——先看本会话有没有新开页（宽限期 1.5 秒，到点还没有就结束，什么也不碰），开了页就让管家试一次 restore（前台还不是 e2k 的 Chromium 就返回 false，下一轮再试），还成了也不结束：直到截止，每次看到前台又是 Chromium 都再还一次（真机实测：弹窗会把浏览器激活两次，第一次还回去之后又被抢走；代价是弹窗出现后约 2 秒内用户自己切到 e2k 的浏览器也会被拉回原应用），从 step 结束起 2 秒到了就放弃，不管前台是什么；任何一轮看到登录窗口在进行（含正在开）就放弃。定时器 `unref`，`shutdown` 把所有睡着的轮询叫醒，它们看到 `stopping` 就结束，不留悬挂的定时器；错误吞掉记日志。同一会话的下一个 step 不取消上一次还没结束的后台还焦点：它只在「前台是 e2k 的 Chromium」时动手，两个同时在跑时，一个还过之后另一个看到前台已不是 Chromium，什么也不做，不会冲突；取消反而会丢掉要还的应用（第二个 step 开始时前台还是 Chromium，它自己 capture 到 null）。时间参数 `SessionDeps.focusTiming` 可注入，测试用手动时钟。开始或结束时任一刻有登录窗口开着、或正在开（`logins.size > 0` 或 `loginsOpening > 0`；后者从 `login.begin` 选好 profile 起、到登记进 `logins` 或失败为止，`finally` 里减，所以启动浏览器和开页的那段窗口里别的 `open` / `step` 结束也不会把前台抢回去）就不还，`login.begin` / `login.end` 不碰焦点。并发的两个会话各自只还各自记下的应用，而且还之前都要核对前台是 e2k 的浏览器，所以不会互相抢回或误伤。`startKernel` 缺省 `macFocus()`（非 macOS 是什么也不做的 `noFocus`），测试一律传 `noFocus` 或假的。

### 5.6 会话和操作

三个动作，会话归内核所有，跨多次 CLI 调用存活：

- `open`：URL、视口、放行声明、可选的 profile 组（不给就由 URL 的域名推出）、可选的触屏模拟（`--touch`，只作用于这个会话的页面，不能模拟时 `open` 失败）→ 会话 id 加首屏读数。
- `step`：一批操作，按顺序执行 → 每个操作的结果。**动作执行失败**（找不到元素、超时）就停下，后面的不执行（批级 `--keep-going` 例外：失败后后面的照跑，失败截图照留，退出码仍按计数算）；**`assert` 不符不算执行失败**，记下结果接着跑。动作失败时结果可带 `hints`（诊断）：选择器匹配了多个就列出总数和前 5 个候选（每个候选一条，可写的 `>> nth=i` 和位置在名字前面），点击被遮挡就带上挡住它的元素；条目可能含页面文字，内核先脱敏、再截到 300（每条）、最多 6 条，记录里页面有密码类字段（或判不出）时只留一句固定说明。
- 每个操作的结果带 `seq`，是整个会话从 1 起的序号，跨批次连续，未执行的操作也占号，和记录、报告里的序号一致，文本输出里叫「序号」。
- `close`：收尾，生成报告。

`step` 里的操作（v1）：

| 类 | 操作 |
|---|---|
| 读 | 文本快照（无障碍树，带元素引用）、取页面文本、截图（默认缩小；可加标签、取整页或某个元素、存成 png、用 `mask` 遮住已知的敏感元素）、读 console、读网络请求摘要 |
| 动 | 点击、填写、按键、悬停、滚动、导航、设视口、等待条件（文字、元素、地址、时间，或页面安静下来的 `idle`） |
| 判 | `assert`：对一个确定值（文案、数量、颜色、字号、间距、URL、可见性）做代码比较，只有相符或不符 |
| 脚本 | 在页面里执行一段 JS 并返回结果。它只有页面脚本的权限，发出的写同样过写策略；拿不到驱动对象 |

- 元素定位统一用一种写法（Playwright 的选择器写法加快照里的引用），由驱动翻译成自己的方言。
- 闲置会话超时自动关闭并出报告；失败时保留最后一屏截图（带 `mask` 的截图失败除外：那张图没有遮罩，不留）。
- 多个会话可并行，但同一 profile 共用登录态。

### 5.7 判定和证据

- **确定值由代码判**：`assert` 的比较是纯函数，不调模型。
- **语义结论由调用的 agent 写**：agent 在 `close` 时提交每条结论和依据，报告里标明「agent 判定」。内核 v1 不调任何模型。
- **`assert` 的结果统一叫「相符 / 不符」**，不叫通过、不通过：复核问题时，`assert` 不符可能正是问题存在的证据，和总结论并排时不能让人误读。
- **总结论有两种口径**：验证改动用「通过 / 不通过」；复核问题用「存在 / 不存在 / 无法判断」。「无法判断」必须写原因（没复现条件、被写策略拦住走不下去、等登录等）。
- **每次运行一个目录**：`report.html`、`result.json`、截图、被拦下的写、被放行的写、用到的批准、域名和当时的模式。
- `result.json` 里有 `blocked`（等登录）和 `next`（下一步该谁做什么）。`blocked` 现在只有 `'login'` 和 `null`：值是会话最后一次登录墙检查（`open` 和每次 `step` 之后各做一次）的结果，收尾时仍停在登录页才是 `'login'`，中途撞到又离开了不算。**M3 没有给 `blocked` 加值**（R8）：等批准是退出码 21、不进记录，身份不符在 `identity` 里（见 5.2），跳到不允许的域名被拦后会话仍可用，所以 deny 的事实记在 `start.deny`、`start.borrowDeny`、`frozen.denied`、`deniedNavigations` 和 `writes.blocked[*].reason = 'denied'`，读报告的人看「不允许的域名」一节，不看 `blocked`。撞到登录墙的实时提示仍在 `open` / `step` 的回应和退出码 20 里（见 5.9）。
- **只读相关的记录**（只加字段，`schema` 仍是 1）：`modes` 是模式变更时间线（`at`、已脱敏的 `host`、`mode`、`reason` 为 `rule` / `forced` / `no-rule` / `host-choice`（没有规则覆盖、模式是登录时选的）、`rulesHash`；和上一条模式相同就不记）；`modes[*]` 另带 `pendingRulesHash`（变化当时待批规则文件的短哈希，没有为 null）；`rules` 是收尾时的规则 `{ hash, count, pendingHash }`：`hash`、`count` 是已批准快照（没批准过是 `{ hash: null, count: 0 }`），`pendingHash` 是同时按「更严合并」生效的待批文件的短哈希（没有待批、或待批是删文件为 null）；`start.readonly` 是 `open --readonly`；`writes.blocked[*]` 带 `reason`（`method`、`graphql-mutation`、`persisted-query`、`redirected-write`、`unattributed`、`other-group`、`denied`）和判定当时的有效 `mode`；`writes.blockedSummary` 把被拦的写按主机 × 方法 × 原因分组计数，未归属的被拦写也在里面（`unattributed: true`），不带路径和请求体；被拦的写没记原因时归入固定的 `unknown`，所以汇总的次数加起来总等于被拦的写的总数。`report.html` 为此多两段：「模式」（时间线表，只有一条且为默认模式时写「全程默认模式」，另列规则条数和哈希）和「被拦下的写（汇总）」（`blockedSummary` 的表，没有时写「没有」）；`blocked` 为 `'login'` 时「环境」一段写「收尾时停在登录页」。**M2b 的收口**：与模式相关的内容集中在「模式」一节下，用 `<h3>` 分四块：「profile」（`start.profile`、`start.borrowed`，环境一段不再写 profile）、「放行声明」、「身份探针」（没配身份整块不出现）、「冻结」（`result.json` 的 `frozen: { group, host } | null`，`group` 为 null 表示判断不出归属，`host` 是第一跳的主机、已脱敏；没冻结整块不出现）。读回老版本的 `result.json` 时缺的字段整块不出现，不抛错。CLI 的 `open` 总是打一行 `profile: <key>`。**M3 的收口**：「模式」一节下再加一块「不允许的域名」（`<h3>`，`start.deny` 的授权、`start.borrowDeny`、`frozen.denied`、`deniedNavigations`，四样都没有整块不出现）。
- **没做的要写出来**：计划了但没执行的检查、被跳过的步骤，在结论区单列，不能并进「通过」。
- **失败分「已恢复 / 未解决」**：`close --superseded '[{"failed":n,"by":m}]'` 声明「序号 n 的失败由序号 m 取代」（序号即 `step` 输出里的 `序号`）。内核在收尾前对着记录校验：`failed` 只能是执行失败或未执行（`assert` 不符不可被取代），`by` 只能是之后完成或相符的操作，同一个 `failed` 不能出现两次；不合格是 usage 错误，会话保持打开、可重新 `close`。报告里两边的操作名和目标取自记录（已脱敏、转义），不取自 agent 的声明；报告分「已恢复的失败」（并排显示，取代者是只读操作或 `wait`、而被取代的是动作时标出；一个取代者取代多个失败时也标出）和「未解决的失败」，没被取代的未执行操作仍在「没做的」里。`tallies` 保持原始计数。
- **按条判定**：`findings` 每条可带自己的 `verdict`，报告里显示在每条前面。结论是 `pass` 时，下面任一条成立算冲突：有不符、有未解决的失败、有未解决的未执行、`--not-done` 非空、有 finding 的判定是 `fail`；`result.json` 的 `conflicts` 逐条列出原因。
- **`eval` 的记录**：源码不进记录，只记 `jsHash`（`sha256:` 加十六进制前 16 位，不加盐）；返回值整体脱敏后截到 1000 字符进记录（`output`）。页面（任一 frame）有密码类字段、或探测不出时不记返回值，改记 `outputOmitted: true`（失败关闭；`eval` 跑前跑后各探一次）；给 agent 的回应不受影响。`eval` 抛错时回应照给（脱敏过）的错误消息，记录只写固定文字并保留 `jsHash`（错误消息可能带着页面值或源码片段）；跑前跑后两次探测拿到的 frame 地址不一致（跑的时候页面换了文档）也按探不出处理。
- **截图不自动脱敏**：图里的内容没法按文字规则处理，已知敏感的元素由 agent 在 `screenshot` 里用 `mask` 遮住（每个遮罩目标至少要匹配一个元素，否则这次截图失败、不出图）；`mask` 只盖元素的包围盒。
- 所有落盘和输出先脱敏：`Authorization`、cookie、token 形态的字符串（整个值像 token 的也算，路径除外）、邮箱（含 `%40` 编码的）、表单和 URL 参数解码后再判的值、自由文本里的 `password=…`、`"token":"…"`、`x-api-key: …` 这类头行和行中间的 `password: …`（含单引号、数字值）、实体或转义引号包着的参数值、URL 编码（最多三层）后才露出的秘密、配置里列出的敏感字段名。选择器（agent 给的目标、内核生成的稳定选择器）给 agent 的回应里原样保留，便于重放；写进 `result.json` 和 `report.html` 时同样过这些规则，命中的部分换成 `[REDACTED]`。
- 报告目录在用户本机，默认不进任何仓库。旧报告按用例或会话名保留最近若干份。

### 5.8 存成用例

- 内核记录了一次会话的全部操作和 `assert`，`save-case` 把它导出成一个用例文件。在 `close` 之后按会话 id 导出。
- **从 M1 起就按可重放来记**：每个动作执行时，把快照里的临时元素引用解析成稳定的选择器一并记下，否则后面要返工。记录里被脱敏的部分（`eval` 源码、没确认安全的 `fill` 值、命中脱敏规则的选择器）不能从记录重放，`save-case` 导出时要标出这些步骤。
- **导出由 agent 挑**：agent 给出要保留的步骤；不给就默认只留执行成功的动作和 `assert`，丢掉试错步骤和纯读操作。
- **语义结论不重放**：重跑时这些条目标成「未判定」，不计入通过。
- **含写的用例不保证幂等**：用例文件里标明「含写」；重跑因数据已存在而失败，如实算不通过。
- `run <用例>`：一条命令重跑，纯代码执行，不需要 agent 在场，输出同样的报告。
- 用例文件包含：起始 URL、profile 组、视口、步骤、放行声明（**不含身份期望**，见下面 M3 的落实）。它带站点信息，默认存在用户指定的位置，不进本仓库。
- 用例里的放行声明照 5.4 走批准；在「只读」域名上批准过的，重跑不再问。
- **M3 的落实（save-case、run，`src/cases/`、`src/cli/commands.ts`）**：两个命令都在客户端做，用现成的 `open`、`step`、`close` 协议，内核没有新方法。**导出**（R10、R11）：按会话 id 在 `runs/*/*-<id>/result.json` 找记录（id 先过 `^s-[0-9a-f]{6}$`，目录用 `resolveInside`，不跟符号链接，记录最大 20 MB），会话 id 会在历史里撞号，所以取目录名最新的那个 `*-<id>`，它没有 `result.json` 就是会话还没 `close`（usage）；只用已脱敏的记录；`--out` 必填、`.json` 结尾、文件已存在就拒绝（不覆盖，`O_EXCL`、0600）、按真实路径落在状态目录之内也拒绝。不给 `--steps` 时留下 `ok` 的 `click hover fill press scroll goto viewport wait` 和执行了的 `assert`（相符或不符），丢掉失败、未执行、纯读和 `eval`；`--steps '[序号…]'`（1–200 个、递增）只留这些，含 `eval` 也行。不能重放的步骤不丢，写成 `{ seq, skip: { op, why } }`：`eval`（用例里不收 `eval`，`parseCase` 也拒绝）、目标是快照引用而记录里没有稳定选择器的步骤（有的就换成选择器）、操作里任一字符串含 `[REDACTED]` 的步骤。起始 URL、任一放行声明或 `open.allow` 的地址含 `[REDACTED]`、记录形状不对、没有放行声明序号（旧内核写的）、选中的步骤超过 500 条或文件超过 1,000,000 字节，一律拒绝导出，不回显内容。**文件格式**（R12）：`{ e2kCase: 1, name, source: { session, kernelVersion }, open: { url, profile, viewport, touch, readonly, allow }, steps, allow, findings: [{ claim }], containsWrites }`；`open.allow` 是人批准打开 deny 主机时的清单（`start.deny.allow`），`allow` 每条带 `seq`（来自 `declarations[*].seq`，也就是提出这条声明的那次 `step` 的第一个操作的会话序号），`containsWrites` = 原会话有放行的写、有放行声明或 `open.allow` 非空。原会话的 claim 超过 500 字就截到 500（终审 F5），不让整份导出失败。**用例里不存身份期望**，和上面「用例文件包含……身份期望」的原文不同：身份每次从批准快照里会话所在的组现取（5.2），存在用例里反而会过期、也会被手改；批准同样不存，用例只能表达请求。用例文件可能被手改，`parseCase` 严格（多余的键、`e2kCase` 版本不对、不合法的 op、含 `[REDACTED]` 或快照引用的可执行步骤、超大、符号链接都在开会话之前以 usage 拒绝，只说哪个字段）。**重放**（R13）：`open`（名字缺省用用例的 `name`，可 `--name`）→ 按 50 个一批顺序 `step`（不 `--keep-going`，有放行声明的序号处切开新的一批、那一批带上这些声明；一批合并后的声明超过 12 条时在 `open` 之前拒绝）→ `close`。有动作失败的一批之后不再发，剩下的算未执行；收到 21 每 2 秒原样重试，每换一个请求 id 重新计 120 秒，同一个 id 等满 120 秒退出 21。**结论由 `run` 代码判**：都相符是 `pass`（没有任何断言也算）；有失败、未执行或不符是 `fail`；有不能重放的步骤（别的都好）是 `undetermined`，`notDone` 逐条列出；`step` 撞登录墙就停、`undetermined`、退出 20（CLI 多打一行「撞到登录墙：请人运行 login 后重跑」，结果里的 `because` 也打成「理由：…」）；`open` 回来身份探针不符（`identity: 'mismatch'`）时和 CLI `open` 同口径：一步不发，`close` 成 `undetermined`（because「身份探针不符」），退出 22（22 优先于 20）。原会话的 findings 只带 claim，`basis` 固定为「原会话里 agent 的判定，重跑不判定」、`verdict: undetermined`。退出码：22（open 时身份不符）> 20 > 11（失败或未执行）> 10 > 0，`open`、`step` 的错误码原样（2、21、22），中途出错时先尽力 `close` 成 `undetermined` 再返回。

### 5.9 agent 面

- **CLI**（暂名 `e2k`）：`start`、`open`、`step`、`close`、`run`、`save-case`、`login`、`status`、`doctor`、`rule`（查看和修改域名规则、域名组）。默认输出给 agent 读的紧凑文本，`--json` 出结构化结果。退出码区分：通过、不符、动作执行失败、等登录、等批准、要人处理、用法或内部错误。退出码只反映代码判的 `assert` 和执行情况（加上下一条的登录墙）；agent 写的语义结论（含「存在 / 不存在 / 无法判断」）在输出和 `result.json` 里，不映射成退出码。
- **退出码 20 已启用（内置启发式）**：`open` 和 `step` 结束时，会话主页面的顶层文档里有可见的密码类字段（`type=password`，或 `autocomplete` 含 `current-password` / `one-time-code`，不含 `new-password`；不进 iframe，穿透 open shadow DOM）就返回 20，并在 `blocked` / `next` 里提示人运行 `login`。20 优先于 10 和 11。它只是提示：会话不暂停、不关闭，也不写进 `result.json`；查不出就不报。域名组里的登录主机识别、跳转到登录主机时的暂停和 `result.json` 的 `blocked`，仍是 M2 的事。
- CLI 里改规则的子命令只是提交一份待批准的改动，批准前不生效。
- **MCP 壳**：一个 stdio MCP 服务，暴露 `open`、`step`、`close`、`run`、`save-case`、`status`、`doctor` 和只读的规则查询。`login`、改规则不经 MCP，由人在终端里做。
- **M3 的落实（MCP 壳，`src/mcp/`）**：`node bin/e2k.js mcp`，手写的 stdio JSON-RPC 2.0（不用 SDK），一行一条消息，单行上限 2 MiB（超了回 `-32600`、id 为 null，丢掉这一行继续）；只认单个对象，数组（批）回 `-32600`，解析错 `-32700`，未知方法 `-32601`；没有 id 的消息是通知、不回应，方法不以 `notifications/` 开头的（比如没带 id 的 `tools/call`）直接丢弃、不执行；支持 `initialize`（客户端给的 `protocolVersion` 在 `2024-11-05`、`2025-03-26`、`2025-06-18` 里就原样回，否则回 `2025-06-18`）、`notifications/initialized`、`ping`、`tools/list`、`tools/call`，没收到 `initialize` 之前的 `tools/*` 也照常处理。工具是 `open`、`step`、`close`、`run`、`save_case`、`status`、`doctor`、`rule_list`，参数走和 CLI 同一套校验，多余的键拒绝；**没有 `login`、改规则、批准类工具**，这些只在终端和弹框里由人做。`tools/call` 的结果是 `{ exit, result }` 或 `{ exit, error }` 的 JSON 文本；`isError` 只在退出码 1、2、22 时为真，10、11、20、21 是正常结果，靠 `exit` 字段区分。请求并发处理，一条回应写完一整行再写下一行；标准输出只写协议消息，等批准的提示写标准错误。
- **使用说明**：一份短文档，讲三个动作、退出码、遇到阻断怎么办。不为某个 agent 写专用 hook。
- **防绕过**：不做拦命令的 hook。依靠两点：profile 被内核进程占着，别的进程打不开同一个 user data 目录；批准不走 agent 的通道。

### 5.10 驱动协议

内核对浏览器只发下面这些操作：

| 组 | 操作 |
|---|---|
| 实例 | 启动（profile）、停止、健康检查 |
| 页面 | 打开（可选按页的触屏模拟：Chromium 用 CDP）、读快照、点击、填写、按键、截图（整页、元素、遮罩、格式）、设视口、等待条件（含页面空闲）、页面内执行脚本 |
| 拦截 | 注册请求拦截回调、注册页面脚本之前的注入脚本、拦导航、重定向各跳的通知（`onNavigationHop`）、清某个主机的 cookie（`clearCookies`） |
| 读数 | 当前位置（顶层 URL、弹窗、frame 列表）、拦截覆盖情况 |
| 收尾 | 关掉本会话开的标签页 |

请求回调的 `RequestInfo` 里和模式判断有关的两个地址：`topUrl` 是顶层框架导航请求的目标，其他请求是发出时那一页主框架的地址（只认 http(s)，否则 null）；`initiatorUrl` 是顶层框架导航请求发出时（路由回调运行时、导航提交之前）主框架已提交的地址，也就是「即将被这次导航替换掉的那份文档」（同样只认 http(s)）；它通常就是发起导航的页，但 iframe 的 `target=_top`、别的窗口的 `target=<窗口名>` 发起的导航，报的是被替换的那一页，不是真正的发送者，其他请求和 `topUrl` 同值。内核用 `initiatorUrl` 定主页面或登录页此刻所在的主机（会话的主页面据此先收敛 topHost 再算有效模式，登录页据此判断回调的发起页是不是 loginHost）。浏览器测试 `initiatorUrl of a form-submit navigation…` 钉住了：表单提交的 `initiatorUrl` 是提交表单那页，经 302 落地后再提交则是 302 的最终地址。

每个驱动声明自己的能力，内核和报告按能力说话：能否网络层拦截、能否覆盖跨进程 iframe、能否拦住原生表单提交、SharedWorker 发出的请求是否都经过拦截（驱动在所有页面删掉 SharedWorker：它的请求不经路由，见 `docs/m0-findings.md` §9.9；做不到就记 `not-covered`，报告提示）、是否共用用户的 profile、能否无头、选择器方言。

**能力不够就不让用在对应的模式上**：驱动做不到网络层拦截时，内核拒绝用它打开「只读」和「不允许」的域名，只能用于「默认」模式；驱动共用用户日常 profile 时，报告里如实标出。

拦截回调的决定是 `continue`（可带 `followRedirects: false`）、`fulfill`（直接回一个响应）或 `abort`。`followRedirects: false` 用于放行的写：Playwright 的路由回调只见重定向链的第一个 URL，307 / 308 的第二跳带着原方法和请求体绕过内核的判断，所以驱动用 `route.fetch({ maxRedirects: 0 })` 自己发首跳。首跳是 3xx 就中止请求，并通知 `onRequestDone({ id, status: 首跳状态, failed: true, redirectRefused: true })`（通知在中止之前发，驱动对每个请求只通知一次，先到为准）；不是 3xx 就把响应原样交给页面；发送出错一律中止，不算重定向。只对同源请求这样发（同源 = 发出请求的 frame 的地址和目标同源，且请求的 `Origin` 头若有则等于目标的 origin；`origin.ts` 的 `isSameOriginRequest`。沙箱 iframe 的 frame 地址同源，但文档 origin 是 null、请求带 `Origin: null`，按跨源，终审 I-5）；跨源请求照常放行，由浏览器自己发，浏览器才继续执行 CORS 和 SameSite（`route.fetch` 不看 SameSite 一律带 cookie，`fulfill` 还会替没有 ACAO 的响应补上 CORS 头）。请求完成通知的形状是 `{ id, status: number | null, failed: boolean, redirectRefused?: true }`。这样发出的请求由 Node 代发：不信任系统额外安装的根证书。

v1 只有 Playwright 驱动。验收标准之一：内核代码里除驱动目录外不出现 Playwright 的类型或调用；另有一个测试用的假驱动实现同一份协议。
